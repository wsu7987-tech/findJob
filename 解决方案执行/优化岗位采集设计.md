# 优化岗位采集设计

## 1. 文档定位

本文用于审阅“岗位采集”页面的整体优化设计。文档按问题拆分，分别描述现象、原因、界面方案、请求优化方案、风险与验收标准，避免把终态恢复、页面抖动、请求过多、状态同步等问题混成一个改动。

当前目标：

1. 保留终态岗位采集任务的恢复和结果查看能力。
2. 明确区分“查看已有任务”和“新建采集任务”。
3. 减少进入页面时的重复请求、重复快照构建和重复实时连接。
4. 降低页面加载期间的布局变化。
5. 统一岗位采集与驾驶舱的状态语义和操作能力。
6. 提取一组低风险、可优先实施的小改动，其余结构性方案提交审阅。

## 2. 已确认的产品边界

### 2.1 终态任务需要恢复

进入岗位采集页面时，若最近一次任务已经完成、失败或取消，页面仍应恢复该任务，用于查看：

- 最终状态与结束原因；
- 已采集岗位；
- 分析结果；
- 执行批次和统计；
- 关联父任务信息；
- 当时使用的执行配置快照。

恢复终态任务本身是正确需求。当前问题是终态任务恢复后，页面仍沿用运行态的订阅、轮询、按钮和编辑逻辑。

### 2.2 新建采集是页面模式切换

“新建采集”表示从终态结果页切换到一个独立的创建模式：

- 不删除后端保存的最近任务；
- 不清空历史结果；
- 新任务草稿拥有独立的配置状态；
- 用户可以返回终态结果；
- 创建成功后再进入新任务的运行态。

这项设计解决的是同一页面同时展示“上一任务结果”和“下一任务表单”造成的语义混乱。

## 4. P1：终态任务仍按运行态恢复

### 4.1 当前表现

终态任务可以被恢复，但恢复后仍可能发生：

- 岗位采集页面建立任务详情 SSE；
- 关联父任务继续启动驾驶舱轮询或 SSE；
- 页面仍展示运行态动作或“下一动作”；
- 状态已经结束，操作区仍提供暂停入口；
- 点击暂停后才由接口返回“Workflow Run 已结束，不能暂停”。

### 4.2 原因

当前逻辑把“恢复任务”和“恢复执行”视为同一件事。实际上：

- 恢复任务：加载快照，允许读取结果；
- 恢复执行：建立实时连接，允许暂停、继续、终止。

只有非终态任务需要恢复执行。

### 4.3 设计方案

对恢复行为建立明确规则：

| 任务状态 | 恢复快照 | 加载结果 | 详情 SSE | 父任务轮询/SSE | 执行按钮 |
| --- | --- | --- | --- | --- | --- |
| active / running | 是 | 是 | 是 | 是 | 按能力展示 |
| paused / waiting | 是 | 是 | 是 | 是 | 展示继续或终止 |
| completed / failed / cancelled | 是 | 是 | 否 | 否 | 不展示执行按钮 |

终态页面只读取最终快照。若用户主动刷新结果，可发起一次性读取，不恢复实时执行链路。

### 4.4 界面方案

终态任务顶部统一展示：

- 终态标签；
- 完成时间；
- 结束原因；
- 最终岗位数量；
- “新建采集”；
- “查看执行详情”；
- 有历史驾驶舱能力时展示“查看父任务记录”。

终态不展示暂停、继续、终止和“下一动作”。

## 5. P2：终态结果与新建表单同时混排

### 5.1 当前表现

终态任务满足“可以开始采集”的条件，因此页面可能同时出现：

- 上一任务的终态提醒；
- 上一任务结果和统计；
- 新任务的配置表单；
- “开始智能采集”按钮；
- 上一任务的 Run ID 或关联信息。

用户难以判断表单配置是上一任务的配置，还是下一任务的新草稿。

### 5.2 页面模式

页面使用三个互斥模式：

| 模式 | 进入条件 | 主内容 | 主操作 |
| --- | --- | --- | --- |
| 运行态 | 当前任务非终态 | 实时进度、岗位、分析与控制 | 暂停、继续、终止 |
| 结果态 | 当前任务终态 | 最终结果、统计、执行记录 | 新建采集 |
| 新建态 | 无任务或用户点击新建 | 独立配置草稿 | 开始采集 |

### 5.3 状态转换

1. 无当前任务：进入新建态。
2. 当前任务非终态：进入运行态。
3. 当前任务终态：进入结果态。
4. 结果态点击“新建采集”：切换到新建态。
5. 新建态点击“返回上次结果”：回到结果态。
6. 新任务创建成功：切换到运行态。
7. 运行任务结束：切换到结果态。

“新建采集”只改变前端页面模式，不删除或覆盖后端当前任务。

## 6. P3：进入页面时发出大量请求

### 6.1 页面级请求清单

| 请求 | 作用 | 当前触发时机 | 问题 |
| --- | --- | --- | --- |
| GET `/api/fine-job/boss-capture/status` | 获取浏览器/采集器状态 | 页面挂载 | 首屏必要，可保留 |
| GET `/api/fine-job/boss-capture/cities` | 获取城市选项 | 页面挂载 | 静态数据重复加载 |
| GET `/api/fine-job/strategies/filters` | 获取筛选策略 | 页面挂载 | 与首屏结果展示无直接关系 |
| GET `/api/fine-job/strategies/recommendations` | 获取推荐策略 | 页面挂载 | 与筛选策略并发，但每次进页重复 |
| GET `/api/fine-job/platform-sessions` | 获取平台会话 | 页面挂载 | 是否首屏必要需要按模式判断 |
| GET `/api/fine-job/smart-captures/current` | 恢复最近任务完整快照 | 页面挂载 | 响应很重，且后续 SSE 会再次返回完整快照 |
| GET `/api/config` | 获取应用配置 | 页面挂载 | 应用层也会请求 |
| POST `/api/config/codex-models` | 读取 Codex 模型列表 | 页面挂载 | 可能调用 CLI，终态结果页不需要 |
| GET `/api/fine-job/smart-captures/{id}/context-snapshot` | 获取上下文快照 | 恢复任务后自动触发 | GET 可能创建数据库快照，成本高于普通读取 |
| GET `/api/fine-job/smart-captures/{id}/analysis-items` | 获取分析项目 | 恢复任务后自动触发 | 涉及多表查询，终态可按分析页签延迟加载 |
| GET `/api/fine-job/boss-capture/tasks/{task_id}` | 获取自定义采集进度 | 活跃任务约每秒一次 | 长时间高频轮询 |

### 6.2 应用级冷启动请求

应用入口还会触发：

| 请求 | 作用 | 与岗位采集页的关系 |
| --- | --- | --- |
| GET `/api/config` | 探测生成能力所需配置 | 与页面级配置请求重复 |
| POST `/api/config/check-codex` 或 `check-llm` | 检查生成能力 | 全局能力探测 |
| POST `/api/config/check-embedding` | 检查嵌入能力 | 全局能力探测 |
| POST `/api/fine-job/boss-executor/desktop-heartbeat-test` | 检查桌面执行器 | 全局启动行为 |
| POST `/api/fine-job/boss-executor/pairing-code` | 心跳失败后的配对处理 | 条件触发 |

因此用户首次打开应用并直接进入岗位采集时，观察到的请求不全来自该页面。

### 6.3 实时连接清单

| 连接 | 作用 | 当前问题 |
| --- | --- | --- |
| 应用级 `/smart-captures/current/events` | 全局感知当前任务 | 页面也建立同类连接 |
| 应用级 `/smart-captures/{id}/events` | 全局任务详情更新 | 与页面详情 SSE 重复 |
| 页面级 `/smart-captures/current/events` | 页面感知当前任务变化 | 与应用级 current SSE 重复 |
| 页面级 `/smart-captures/{id}/events` | 页面实时刷新任务 | 终态仍可能建立 |
| 页面级 `/workflow-runs/{id}/events` | 同步关联父任务 | 终态父任务仍可能启动 |

活动且关联父任务的冷启动场景，可能同时出现约 14–16 个 REST 请求和 5 条 SSE 长连接。数量会随能力探测结果和回退路径变化。

### 6.4 为什么这些请求会让页面持续变化

当前 Smart Capture 完整快照包含较多数据：

- 全部批次；
- 批次岗位快照；
- 当前内存采集任务；
- 搜索组合；
- 候选池；
- 预取数据；
- 岗位列表；
- 关联 Workflow Run；
- Workflow Run 的任务、采集岗位、子任务和上下文快照。

同一次冷启动中，这份完整快照可能被重复构建和传输：

1. 页面 GET current；
2. 应用级 current SSE 首帧；
3. 应用级 detail SSE 首帧；
4. 页面级 current SSE 首帧；
5. 页面级 detail SSE 首帧。

如果存在父任务，Workflow SSE 还会发送另一份完整运行快照。前端收到不同请求的结果后分别更新城市、策略、模型、任务、上下文、分析项目和父任务区域，导致模块按返回顺序出现，页面高度和内容持续变化。

### 6.5 请求优化方案

#### 第一层：立即停止无意义请求

- 终态任务不建立任务详情 SSE；
- 终态关联父任务不启动轮询或 SSE；
- 终态结果页不加载 Codex 模型列表；
- Context 改为展开或点击后加载；
- 分析项目进入“分析”页签时再加载；
- 自定义任务只在非终态轮询，离开页面立即停止。

#### 第二层：复用前端已有数据

- 城市、筛选策略、推荐策略增加一次加载标志和显式刷新入口；
- 同一应用会话内复用已加载配置；
- 对并发中的同一个请求复用同一 Promise，避免多个组件同时发起；
- 路由返回时先使用 Store 中的数据，再按数据失效规则后台更新。

缓存需要明确失效条件，例如配置保存成功、策略修改成功或用户主动刷新。此项应在审阅后实施，避免页面长期显示旧数据。

#### 第三层：统一实时数据所有权

应用级控制器负责：

- current SSE；
- 当前活动任务的 detail SSE；
- 向页面 Store 分发状态。

岗位采集页面只订阅 Store，不再建立第二组 current/detail SSE。页面离开后，全局通知能力仍可保留。

如果产品不需要跨页面通知，可以反向选择“页面独占实时连接”。两套方案只能保留一套。

#### 第四层：拆分后端快照

将 current 接口调整为轻量摘要：

- capture_id；
- status；
- stage；
- state_version；
- linked_workflow_run_id；
- 关键计数；
- started_at / completed_at；
- waiting_reason / terminal_reason。

岗位列表、批次、分析、Context、父任务详情按页签或模块单独加载。SSE 默认只推送摘要和版本变化，具体模块在版本变化后按需刷新。

该方案收益最大，也会改变接口契约，需要单独审阅。

#### 第五层：替换高频轮询

自定义采集任务的每秒 GET 可改为：

- 复用任务 SSE；
- 或运行态使用较低频率并采用固定刷新节奏；
- 页面不可见时暂停；
- 终态立即停止。

## 7. P4：状态表达重复并互相冲突

### 7.1 当前表现

状态可能同时出现在：

- 采集概览；
- 智能采集详情；
- 顶部提醒；
- 父任务卡片；
- Planner 区域；
- 进度区域；
- 驾驶舱。

当各区域使用不同字段或刷新时机时，会出现“父任务状态：active”与“父任务已结束”同时展示。

### 7.2 统一状态模型

顶部任务状态头作为唯一权威表达，其他模块只展示自己的业务信息。

状态头字段：

- 当前任务名称或 ID；
- 归一化状态；
- 当前阶段；
- 开始/结束时间；
- 等待或结束原因；
- 允许的操作。

操作按钮必须从“归一化状态 + 后端能力”派生，不能只根据本地 pollingActive 或是否存在 Run ID 决定。

### 7.3 终态文案

- “下一搜索范围”改为“最终搜索范围”；
- “下一搜索组合”改为“最终搜索组合”；
- 隐藏“下一动作”；
- “父任务已结束”与父任务状态标签使用同一归一化结果；
- 已结束任务不出现暂停按钮。

## 8. P5：页面信息架构过长

### 8.1 当前问题

页面目前按执行模块纵向堆叠。用户最常查看的岗位与分析结果被浏览器状态、父任务、Planner、配置、进度和高级工具推到较下方。

### 8.2 建议布局

#### 顶部固定区域

- 环境状态条：浏览器、平台登录、执行器；
- 任务状态头：当前任务状态、关键计数、主要操作。

#### 主内容页签

1. 概览：关键指标、阶段、最近事件、结束原因。
2. 岗位：岗位列表、筛选、批次。
3. 分析：分析队列、分析结果、人工分析。
4. 执行详情：Planner、组合、过程日志、父任务摘要。
5. Context / 高级工具：上下文快照、诊断信息。

#### 新建态

新建态只展示：

- 创建表单；
- 配置校验；
- 开始采集；
- 返回上次结果。

不同时展示上次任务的大量执行详情。

## 9. P6：页面加载期间布局持续变化

### 9.1 原因

首屏没有明确的初始化边界。各请求完成后分别插入模块，造成页面高度、按钮位置和信息顺序变化。

### 9.2 稳定首屏设计

页面初始化只等待三个决策数据：

1. 浏览器状态读取完成或明确失败；
2. 当前任务身份与状态确定；
3. 页面模式确定。

完成后一次性呈现稳定骨架。其他模块在固定容器中独立加载：

- 城市和策略加载不改变表单整体位置；
- 模型列表只更新模型选择控件；
- Context 和分析页签未打开时不加载；
- 岗位列表使用固定高度骨架；
- 错误显示在对应模块内，不触发整页替换。

建议避免全屏遮罩反复出现。首次初始化可使用一次页面骨架，后续刷新使用局部加载状态。

## 10. P7：当前任务配置与新任务草稿混用

### 10.1 当前问题

页面中的 `smartExecutionConfig` 更接近新任务默认草稿，但恢复任务后，界面又展示当前任务标识和结果。两类数据并没有清晰的所有权。

### 10.2 数据模型

拆分为：

- `restoredExecutionConfigSnapshot`：当前或终态任务创建时使用的只读配置；
- `newCaptureDraft`：用户新建任务时可编辑的草稿；
- `draftDirty`：草稿是否被用户修改；
- `pageMode`：运行态、结果态或新建态。

### 10.3 交互规则

- 结果态显示只读配置快照；
- 点击新建时，从系统默认值或用户模板初始化新草稿；
- 是否支持“复制上次配置”由独立按钮表达；
- 新草稿不自动回写已完成任务；
- 终态任务的分析指导不提供保存入口，除非产品明确支持历史任务再分析。

## 11. P8：终态父任务入口与驾驶舱规则不匹配

### 11.1 当前问题

岗位采集可以恢复终态并显示关联父任务，但驾驶舱目前只恢复非终态任务。终态页面点击“返回驾驶舱”后，驾驶舱可能没有对应历史 Run。

### 11.2 可选方案

方案 A：驾驶舱增加历史查看路由，例如携带 `workflow_run_id` 打开只读详情。

优点：父子任务链路完整。  
缺点：需要驾驶舱支持按 ID 加载历史 Run。

方案 B：终态结果页只显示父任务摘要，不提供跳转。

优点：实现简单。  
缺点：用户无法继续查看完整父任务过程。

建议采用方案 A，并作为结构性优化单独审阅。

## 12. 当前工作区已完成、需要保留的优化

以下行为已在当前工作区调整，后续设计和实现应保留：

- current 接口返回完整快照时直接使用，避免紧接着再次 GET 同一详情；
- current、基础数据和配置请求并发启动；
- Context 与分析项目并行加载；
- 仅在任务身份、语义状态、阶段、当前批次或等待原因变化时刷新关联数据，不因每次 `state_version` 变化全部刷新；
- 页面卸载时停止页面级订阅；
- 驾驶舱只恢复非终态任务；
- 终态任务控制按钮增加状态约束。

由于当前没有测试授权，本节只记录实现状态，不把它们标记为已验收。

## 13. 可马上处理的低风险问题

以下改动范围局部，不改变后端业务契约，适合作为第一批实施。任何代码改动仍需定向测试或人工验证，不能承诺绝对不会出现缺陷。

### 13.1 第一批建议

1. 终态任务不建立 detail SSE。
2. 终态父任务不调用 `startPolling`，不建立 Workflow SSE。
3. 终态隐藏暂停、继续、终止和“下一动作”。
4. 终态文案改为“最终搜索范围”“最终搜索组合”。
5. Context 改为用户展开或点击后加载。
6. 新建表单中移除上一任务 Run ID，把任务标识放在结果态或运行态状态头。
7. Codex 模型列表仅在新建态且相关控件可见时加载。
8. 各模块错误就地展示，避免一个辅助请求失败导致整页状态变化。

### 13.2 第二批建议

1. 城市、策略和配置增加 Store 级复用与明确失效规则。
2. 页面不可见时暂停自定义任务轮询。
3. 进入“分析”页签时再请求分析项目。
4. 结果态与新建态使用独立容器，先完成视觉分离。

第二批涉及缓存时效或页面状态拆分，建议在审阅确认失效规则后实施。

## 14. 需要审阅后再实施的结构性优化

1. 引入运行态、结果态、新建态三个互斥页面模式。
2. 重构为“概览 / 岗位 / 分析 / 执行详情 / Context”页签。
3. 统一应用级与页面级 SSE，只保留一个实时数据所有者。
4. 将 current 和 SSE 快照改为轻量摘要。
5. 将岗位、批次、分析、Context 和父任务详情拆成按需接口。
6. 以事件推送或低频刷新替换每秒轮询。
7. 为驾驶舱增加按 Run ID 查看历史任务的只读路由。
8. 将当前大页面拆分为状态头、结果区、创建区、岗位区、分析区和高级工具区。

## 15. 建议实施顺序

### 阶段一：终态语义修正

- 停止终态 SSE 和父任务轮询；
- 修正按钮能力；
- 修正终态文案；
- Context 与模型列表改为按需加载。

预期结果：请求数量立即下降，终态任务不再表现为仍在执行。

### 阶段二：界面模式分离

- 引入三个页面模式；
- 分离结果快照与新任务草稿；
- 增加“新建采集”和“返回上次结果”切换。

预期结果：用户可以明确判断当前是在看结果还是创建新任务。

### 阶段三：请求所有权收敛

- 合并重复 SSE；
- 增加 Store 复用与失效机制；
- 优化轮询。

预期结果：降低重复传输和重复状态提交。

### 阶段四：接口和信息架构重构

- 拆分轻量摘要与重数据；
- 重组页面页签；
- 增加历史驾驶舱入口。

预期结果：首屏稳定、页面更短、重数据按需加载。

## 16. 验收矩阵

| --- | --- | --- | --- | --- |

## 17. 审阅时建议补充的网络证据

实施前可在浏览器 Network 面板分别记录以下场景：

1. 冷启动且无当前任务；
2. 冷启动且存在活动独立任务；
3. 冷启动且存在活动关联任务；
4. 冷启动且存在终态任务；
5. 从其他页面返回岗位采集；
6. 活动任务自然进入终态。

每个场景记录：

- REST 请求总数；
- 重复 URL 与响应体大小；
- SSE 连接数量；
- 首次稳定呈现时间；
- 最后一次布局变化时间；
- 后端完整快照构建次数；
- Context 是否发生隐式创建；
- 自定义任务一分钟内轮询次数。

这些数据用于确定拆分接口的收益，不作为第一批低风险修复的前置条件。

## 18. 待审阅决策

1. 终态父任务是否必须支持跳转到历史驾驶舱。
2. 新建草稿默认使用系统默认值，还是复制上一次任务配置。
3. 应用是否需要跨页面 Smart Capture 实时通知。
4. Context 是只在高级工具中展示，还是需要在概览中提供摘要。
5. 终态任务是否允许重新执行分析；若允许，应以新分析任务表达，避免修改历史快照。
6. 城市、策略和配置的缓存失效规则。
7. current 接口是否允许调整为轻量摘要。

## 19. 结论

岗位采集当前需要分别处理四条主线：

1. 终态任务保留恢复能力，同时停止所有运行态行为；
2. 结果查看与新建采集使用互斥页面模式；
3. 收敛首屏 REST、SSE 和轮询，减少重复完整快照；
4. 重组界面层级，让任务状态、岗位结果和分析结果优先呈现。

第一批可以先处理终态订阅、父任务轮询、按钮、文案和按需加载。这些改动局部且不改变后端接口。页面模式、统一 SSE、轻量快照和历史驾驶舱属于结构性改动，提交审阅后再实施。
