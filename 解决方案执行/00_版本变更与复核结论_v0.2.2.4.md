# v0.2.2.4 封版变更与复核结论

> 本版以 **v0.2.2.3 为直接基线**，只封死一条产品语义（hard failure 后的父层决策）；不新增任务、不改变产品模型、页面范围和 00→16 执行顺序。

本次封版小修共 1 项：

1. **hard failure 后的父层决策与 child stop 对齐**：`child_failed_waiting_decision` 与 `child_cancelled_waiting_decision` 共享同一决策集合——跳过该 child 继续后续编排 / 结束父任务，二选一。此前 v0.2.2.3 及之前版本把这一点列为"本轮不擅自新增，Luna 遇到时报告"的开放项；v0.2.2.4 由产品方（用户）确认后封死，Luna 不再需要为此暂停任务。skip 不改变该 child 的 `failed` 终态、不暴露 retry，只是父编排跳过该 child 继续后面的步骤。

受影响文件：`E_状态_子任务_事件与实时传输契约.md`、`B_父子任务控制状态矩阵.md`、`03_Luna_父子控制_失败中断与卡点状态机.md`、`12_Luna_新驾驶舱编排UI与快递式时间线.md`、`Codex_Luna_每窗口通用提示词_v0.2.2.4.md`、`16_Sol_Terra_高风险复核清单_v0.2.2.4.md`、总览第 9 节。

## 一、版本结论

v0.2.2.4 以 **v0.2.2.3 为直接基线**。v0.2.2.3 已封死的 failed/retry hard terminal、`child_state_version` 单调递增防乱序、linked-only outcome event、Smart Capture API 路径统一等全部继续有效；v0.2.2.2 及更早版本确认的双层 authority、ExecutionConfig owner、Pipeline owner、08A/08B 拆分、reservation 策略和历史兼容原则同样继续有效。本版不重新设计任何产品行为，只是把 v0.2.2.3 里唯一还留白的"hard failure 是否允许 skip"补齐，避免 Task 03/12/16 到时候还要停下来找产品确认。

完成本版本补充后，才建议开始按任务编号执行。

## 二、继承并继续有效的 7 类硬契约

### 1. Pipeline Schema owner 逐表落地

补充了每一类 Pipeline 数据的 Smart Capture owner、parent/history link、independent 可为空字段、FK、唯一约束、SQLite 重建要求和升级验收。

特别覆盖：

- Search Combination / Discovery；
- Candidate / Workflow task 中的 JD、Analysis item；
- Context snapshot；
- Analysis handoff；
- Prefetch batch/item；
- Candidate reservation；
- Evaluation feedback；
- Codex session / handoff 关联。

不能只给旧表增加一个 `smart_capture_id` 字段后继续依赖 `workflow_run_id`；independent Smart Capture 必须在没有 Workflow Run 的情况下完成全部 Pipeline 持久化。

### 2. 状态、等待原因和控制来源统一

`E_状态_子任务_事件与实时传输契约.md` 明确：

- Smart Capture 的合法生命周期状态；
- parent 的 legacy `status` 与新的语义控制状态如何并存；
- `waiting_reason`、`control_cause`、`state_version` 的含义；
- `waiting_child_paused`、`child_failed_waiting_decision` 等状态不得由不同模块自行解释。

“或等价状态”不再允许成为未定义实现的借口。若采用不同字段名，必须提供同等 API 契约和迁移证明。

### 3. 通用 child relation、事件幂等和竞态处理

父层必须拥有持久化的通用 child relation，不能只把 child 信息塞入 Workflow payload 或前端状态。

补充了：

- child 顺序和类型；
- child ref、result summary、capabilities；
- transition id / state version；
- child completion event 的幂等键；
- parent pause/cancel 与 child 回调之间的优先级和竞态规则。

### 4. Smart Capture snapshot / polling 与旧执行入口切断

明确 Smart Capture 必须提供独立的 snapshot/polling 契约，independent 不依赖 Workflow SSE。

同时把当前源码中必须在 Cutover 后停止或委托的入口列为硬验收：

- `workflow_runs._on_capture_task_updated`；
- `workflow_runs._advance_after_capture_finished`；
- `advance_deep_job_search` 作为 live Engine；
- `resume_smart_capture` 中的 resume + advance 组合；
- App-level Workflow Codex controller；
- 任何“找不到 Smart Capture 就回退 Workflow live execution”的 fallback。

### 5. 完整 Smart Capture 配置 owner

补充要求完整的岗位采集执行配置由 Smart Capture 持有，不能只有搜索字段在 Smart Capture、投递目标和 Codex 字段仍只存在 Workflow contract。

linked 与 independent 必须使用同一个配置模型，包含 delivery target、Candidate/JD、Analysis、Codex、Recommend/Review、Context budget、stop policy 等字段。

### 6. OFF completed 后处理不得走回滚路径

完成状态下的 Manual Analysis / 人工选岗位送 Codex 必须使用 Smart Capture 后处理入口，或使用经过证明不会改变生命周期的兼容适配器。

不得调用会把 completed capture 或已推进 parent 改回 running / waiting 的旧 Workflow 函数。

### 7. hard failure 与 child stop 共享同一父层决策集合（v0.2.2.4 新增确认）

`child_failed_waiting_decision` 不再是"只保证不误推进、skip 语义留白"，而是与 `child_cancelled_waiting_decision` 使用相同的两个动作：跳过该 child 继续后续编排 / 结束父任务。这不改变 `failed` 是 hard terminal、同一 child 不可 retry 的既有规则；skip 只是父编排层面跳过该 child，不是让 child 复活。

## 四、执行门槛

如果 Luna 在实现过程中无法回答以下问题，应暂停当前任务并报告，而不是自行选择：

- independent Pipeline 记录具体落在哪些 owner 字段；
- parent waiting 状态具体如何存储和返回；
- child relation 使用哪张持久化表；
- linked completion event 是否带 `child_relation_id/child_type/child_ref`，并按 `(child_relation_id,event_id)` 只消费一次；independent 是否不产生 parent event；
- event `state_version` 是否明确是 child lifecycle version，relation 是否保存 `child_state_version` 并只接受更高版本，而 parent relation `state_version` 独立递增；
- Smart Capture 页面如何在没有 Workflow ID 时获得实时快照，且不存在第二套 `revision`；所有 snapshot 可观察变化是否单调递增 `state_version`；
- Cutover 前最小 completion/outcome 闭环是否已经通过，Cutover 后哪个旧入口被禁用或委托；
- `waiting_for_user` 新写入/API 是否 canonical，legacy `waiting_next_batch + waiting_reason` 是否只存在于迁移/读取适配；`failed` 是否 hard terminal 且 retry=false；
- completed OFF 的 Manual Analysis 如何保证不回滚生命周期；
- `child_failed_waiting_decision` 下的 skip / end 两个按钮是否都已实现，且 skip 后该 child 是否仍保持 `failed`（v0.2.2.4 新增门槛，不再属于"未确认可跳过"）。
