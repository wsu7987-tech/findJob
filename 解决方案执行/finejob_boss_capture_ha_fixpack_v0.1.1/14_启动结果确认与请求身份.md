# 14 / 启动结果确认与请求身份

文档修订：2026-09-26-r1。本次必需任务，承接 01 的有限超时和 12 的慢启动检查。本轮接口、表和接线已实现；实现选择及有限运行证据见 16，完整场景状态见 08。

## 1. 为什么必须补齐

客户端超时/取消不等于后端取消。现有 active 查询只表示容量占用，可能返回 `custom-reservation:*`，也会漏掉已快速结束的任务；Smart Capture current 也不能证明一个尚在探测的请求最终不会创建任务。

因此 current/active 只能辅助同步，不能作为“创建失败，可以重新提交”的证明。完整控制幂等仍延后，但本次涉及真实启动的用户意图必须能查到明确结果并防止重复副作用。

## 2. 范围及存储变更

覆盖用户发起的 custom 首次采集、继续列表、手动/历史详情，以及 Smart Capture create/start/resume/retry、会实际恢复采集的父 Workflow resume/child start 和对应 Codex 工具。暂停、停止、分析控制的完整幂等链路仍按后续 04 处理；本次也不为它们自动重放。

本补齐版明确允许一项计划内的增量数据库迁移：新增轻量启动回执表，建议名 `fj_collection_start_operations`。这是对原“本次无数据库迁移”的范围修订，不是已经执行迁移。

复用项目现有迁移机制，不新增依赖；不重构原采集表和状态机。回执至少包含：

| 字段 | 用途 |
| --- | --- |
| `operation_id` | 客户端每次用户意图生成的 UUID，唯一键 |
| `action`、`owner_kind`、`owner_id` | 操作及目标；首次创建 owner_id 可空，另保存真实结果引用 |
| `request_identity_json` | 规范化后的启动业务参数，直接比较；排除 operation_id、transition_id 等无关字段 |
| `status` | `pending / started / rejected / unknown`，仅表示启动请求结果 |
| `phase` | `validating / checking_browser / opening_browser / checking_login / dispatching / finished`，用于启动区显示，不改业务 task stage |
| `result_kind`、`result_task_id`、`result_phase_ref` | 真正任务/阶段引用，禁止填临时容量预占 ID |
| `error_category`、`message` | 可解释的拒绝或不确定原因，不保存 JD、Context、登录数据 |
| `created_at`、`updated_at`、`executor_epoch` | 时间和执行进程代次，用于重启恢复 |
| `closed_without_dispatch` | 未进入执行且已确认关闭的意图标记；阻止迟到原 POST 再启动，见第 5 节 |

既有记录不回填虚构 operation。新增可选 `operation_id` 到既有启动请求并更新所有本轮调用方；旧调用方未传时由服务端生成并返回，但明确其响应丢失后不能按客户端意图可靠查询，旧接口兼容不等于具备新恢复保证。

未决记录不可自动清理。已结束记录本轮不设自动过期，避免过期后误判成新意图；独立维护清理策略列为后续，不能复用已删除的 ID 静默重放。

## 3. 请求与查询契约

建议新增只读端点：`GET /api/fine-job/collection-start-operations/{operation_id}`。由统一回执服务供 HTTP 和 Codex 工具共用；对应工具需支持按 operation_id 查询。

| 结果 | 含义与前端行为 |
| --- | --- |
| `pending` | 服务端已登记，仍在校验/启动；提示“正在确认启动结果”，禁止新建替代意图 |
| `started` | 已确认执行器接收启动/恢复，或已有可核对的实际执行结果；读取真实任务状态，不直接等同业务 running 或成功完成 |
| `rejected` | 已确定本次未启动执行器/未提交该阶段；显示原因，允许用户修正后以新 ID 提交 |
| `unknown` | 存在不能证明的副作用或进程中断窗口；保留结果与未决意图，禁止自动或换 ID 重试 |
| 查询 404/网络错误/超时 | 表示尚未查明，不是 rejected；保留未决状态并继续有限频率查询 |

首次 POST 成功保持原任务响应主体，附带 `operation_id` 和 `response_type: task`；已完成相同请求返回同一结果引用。查询或相同 ID 正在执行时返回带 `response_type: operation_receipt` 的回执，重复请求的 pending 使用 HTTP 202。前端用显式判别字段解析两种响应，不能仅凭 202 当作任务。相同 ID、不同 action/owner/参数返回 409 `START_OPERATION_CONFLICT`，不能执行第二次副作用。

业务拒绝沿用 AppError HTTP 状态/分类，并带可查询的 operation_id。数据库或连接错误不能伪装成已登记的回执；客户端收到非确定性错误仍按未知处理。

## 4. 服务端执行顺序

1. 解析参数与身份权限；拒绝明显无效请求，不打开浏览器。对于合法启动意图，在短事务内登记唯一 operation、检查现有业务容量并取得该意图的启动占用。
   对可解析 operation_id 的参数/权限/容量拒绝也记录 rejected；无有效 ID 且框架明确在业务调用前拒绝的参数错误，作为确定未派发处理。普通 500、网关错误不能如此推断。
2. 相同 ID/相同参数已登记时只返回已有状态，绝不再次启动 worker；同一容量域的其他启动意图需等待或明确冲突。启动占用与业务容量的关联必须包含 operation_id，避免把自己的占用当成冲突；不能用前端按钮锁代替后端互斥。
3. 在数据库事务外执行浏览器/页面/实时登录检查；同时保存原 owner、状态版本与控制意图。不得持有 SQLite 写锁进行 CDP 等待。
4. 成功后重新校验容量、owner、版本与父权限。等待期间任务被停止、父控制改变或 current 更换时，结束本次意图，不覆盖新的状态。
5. 使用既有原子创建/父子控制边界落地真实任务或阶段关联。新增任务使用服务端预分配的真实任务 ID，回执绑定与任务身份持久化必须同事务提交；需要调整 `boss_capture_tasks.py` 的内部创建入口，使其可接收可信的预分配 ID/事务，不接受客户端任意伪造 task_id。
6. 事务提交后才启动实际执行器；只有执行器启动已确认才将回执置为 started。提交到启动确认之间仍为 pending；若崩溃或结果不可确定，转 unknown，并按既有恢复规则将已绑定任务标为可解释的 interrupted/failed，不能宣称从未创建。
7. 已有任务的恢复/续采也记录稳定阶段引用与原始版本，先绑定回执，再提交状态并启动执行器。失败时按实际发生阶段处理，不能无条件恢复旧快照覆盖并发停止。
8. 无副作用的检查失败可记 rejected 并释放本次占用；已经创建/派发但后续响应失败只允许 started 或 unknown。异常路径均由统一回执服务处理。

启动占用在成功后交给既有业务容量；明确拒绝时释放。unknown 若仍无法排除活跃执行器，保留有效占用并提供状态查询，不能只因超时自动释放。pause/stop 与状态读取不受启动占用阻塞。

## 5. 重启与结果恢复

- 后端启动时检查旧 executor_epoch 的 pending，按 operation 绑定的真实结果及既有恢复事实归并；不自动重跑未决请求。
- 能找到真实任务/阶段记录时返回其引用和当前状态；如其执行已中断，明确报告中断而非 running。
- 能证明未创建任务、未提交阶段、旧执行进程已退出且没有派发可能时才可转 rejected。无法证明则保留 unknown。
- custom 快速完成、失败、历史详情等必须仍能通过回执找到真实引用与最小结果摘要；不得只依赖 active 或进程内任务字典完成确认。结果内容按既有历史读取，回执只保存必要确认事实。
- 如果 operation 查询始终无记录（例如请求从未送达），前端不能自动生成新 ID 再提交。提供“检查启动结果”和下述安全确认结束入口；不能把固定等待时长当作失败证明。

### 无记录/未派发意图的安全退出

为避免请求从未送达时永久锁住开始按钮，新增 `POST /api/fine-job/collection-start-operations/{operation_id}/resolve`，并为 Codex 提供等价操作。该操作只确认并关闭未派发意图，不启动任务、不取消已经运行的任务；由用户点击“确认结束未开始的请求”触发，不自动调用。

- 使用与启动登记相同的事务互斥。记录不存在时插入持久化 rejected 标记（`closed_without_dispatch = true`），随后迟到的原启动 POST 看到该标记必须拒绝，不能重新取得执行权。
- 已存在且当前 epoch 仍持有执行权、已绑定任务/阶段或无法排除副作用时，不作关闭，返回 pending/started/unknown 及原因。仅在恢复流程证明旧执行进程已退出且从未派发时，允许转 rejected。
- 已关闭的 ID 不论后续参数如何都不能启动；该标记按当前调用方/本地后端权限校验，不允许跨授权范围关闭别人的操作。
- 返回 rejected 后前端才清除未决锁，下一次用户意图使用新 ID。resolve 自身响应丢失时重复查询/同一 resolve 只返回相同关闭结果，绝不触发实际启动。
- 此路径纳入 OP-06：同时模拟“先关闭后迟到 POST”和“POST 已取得执行权后关闭”，前者永不启动，后者不能被误标为从未派发。

## 6. 前端与 Codex 调用方

- 在真正发送启动 POST 前生成 operation_id，并在当前后端作用域持久保存 `{operation_id, action, owner, submitted_at}`；不存完整请求或敏感业务内容。
- 同一提交进行中只使用一个 ID。刷新/路由切换/模式切换保留未决意图；返回页面和应用重开时先查询回执。
- loading 表示当前网络等待。HTTP 请求结束应释放 spinner，但“结果未确认，禁止重复启动”的控制锁单独保留，避免无限 loading 与重复提交二选一。
- 查询采用 1、2、5、10、15 秒退避并有限次自动尝试，例如 6 次；之后停止自动查询，保留未决状态和手动确认入口。单次查询仍有超时；网络恢复可合并触发一次查询。
- POST 等待期间需要显示阶段时，复用同一查询协调器，最多每 2 秒一次；同一 operation 不开两条查询循环，POST 结束后切入上述退避。回执读取不阻塞主进度 SSE。
- started 后加载真实任务：同步失败显示“启动已受理，状态同步失败”；真实任务已完成/失败则显示实际结果。
- rejected 后允许新用户意图；unknown、404、查询失败不可通过清空 Store、换模式或改 ID 解锁。
- 无记录或已确认未派发时可使用第 5 节 resolve 路径结束旧意图；不允许用纯前端“忽略错误”替代服务端关闭标记。
- 非启动控制（pause/stop）响应未知时查询具体任务状态，不做自动重放；必要时显示待确认提示，保留停止等安全控制入口。

## 7. 对后续完整幂等的边界

本次已包含“启动意图去重＋结果回执”，不能仍写成“所有幂等改造均后续”。后续 04 继续负责暂停/停止/分析控制等全链路稳定 transition_id、完整副作用幂等和 Context 纯读；本轮不实现自动写重试或通用命令总线。

## 8. 验收

新增 `OP-01～OP-06`，并覆盖 `RQ-04、ST-05、ST-08`：

- POST 在登录检查期间超时，current/active 为空，前端仍保持未决；后端后续启动后能按同一 ID 找到结果。
- 相同 ID 并发两次，只调用一次探测和实际启动；不同参数复用 ID 返回冲突。
- custom 查询出现临时预占 ID 时不把它传给 task API；任务快速完成后仍可查询回执。
- 拒绝登录检查不创建首次任务；恢复检查失败保留原任务和父子状态。
- 页面卸载/模式切换/应用重开后恢复未决意图；spinner 结束但重复启动仍被阻止。
- 通过替身覆盖“登记后、任务绑定后、执行器确认前”的中断窗口，结果不明不自动重发；不杀用户后端进程。
