## 2. 全入口接入矩阵

下列“检查前”包含参数、任务存在性、操作能力、父权限和容量；“状态后”只能发生在必要检查成功及提交前重验之后。

| 入口 | 检查前的真实目标 | 检查后的操作 | 关键要求 |
| --- | --- | --- | --- |
| custom `/capture` | 尚未创建的新任务 | 创建真实任务并启动 | 拒绝时无首次任务；按 14 绑定回执 |
| custom `/tasks/{id}/continue` | 原任务、原列表 target、剩余列表能力 | 原页继续下滑 | 原 target 丢失不重建游标，见第 5 节 |
| custom `/tasks/{id}/details` | 选中岗位及详情操作权限 | 创建详情阶段 | 可使用新的详情页，不能改动列表续采绑定 |
| 历史岗位详情入口 | 历史岗位存在、规则允许 | 独立详情执行 | 回执保存真实执行引用，即使快速结束 |
| Smart Capture create | 执行配置和容量 | 创建 Smart Capture 与首批 | 登录通过前不创建首次身份 |
| Smart Capture pending start/retry | 既有 pending/interrupted owner | 启动允许的批次 | failed 终态依旧不可重试 |
| Smart Capture resume | 原列表/正式 JD/预取的实际恢复目标 | 恢复对应阶段 | 仅即将调用浏览器的分支探测；不把所有恢复强行归为列表 |
| 父 Workflow resume | 父暂停原因、child 状态、实际执行单元 | 既有父子原子恢复及执行器恢复 | 先检查再改状态；失败不能留下父/child 假 running |
| 父 Workflow child start / linked adapter | 父权限、pending child、生产执行权 | 进入同一 Smart Capture 启动服务 | 检查结果只在同一服务调用内部传递 |
| Codex custom start/continue/details/history | 与对应 HTTP 相同目标和权限 | 调同一业务启动服务 | 工具 schema 传 operation_id，暴露回执查询 |
| 运行中的自动批次/正式 JD/预取接续 | 当前引擎的既有执行授权 | 原有自动接续 | 不为每页/每个详情新增完整登录探测；运行中失效沿用采集器处理 |
| pause、stop、纯结果查看、纯父控制决策 | 无新浏览器采集 | 既有控制或查询 | 不要求浏览器登录，不被未决启动锁阻止 |

实施时做一次入口引用搜索，核对 `start_capture`、`continue_capture`、`resume_paused_capture`、`start_details`、`start_history_detail` 的所有用户触发路径。不能仅给两个主路由加检查就宣称 ST-06 通过。

## 3. 前端启动顺序与阶段

1. 校验当前模式表单；立即设置本次提交状态，防止容量检查期间重复点击。
2. 已有未决 operation 时进入其查询流程，不另建启动意图；读取活动任务作容量提示。
3. 生成并保存 14 的 operation_id，发送一次启动请求。实际浏览器打开与实时探测由后端统一执行，前端不在该链路另调一次完整登录探测或独立打开页面。
4. 请求仍在等待时，可合并查询回执 phase 来显示“检查浏览器 / 打开浏览器 / 检查登录 / 准备采集”；在尚无 phase 时只显示“正在准备启动”，不虚构已经完成的检查。
5. 服务端实际受理后读取真实任务/current。启动成功但同步失败展示准确提示，不说未创建。
6. finally 释放本次网络 loading；pending/unknown 的提交锁按 14 保留，显示确认入口。确定 rejected 才允许修正后使用新 operation 再开始。

浏览器未启动时开始按钮可用；禁用由表单、控制能力、已知容量及未决意图决定。手动“打开浏览器”“检测登录”入口保留，但不替代本次后端实时检查。

回执 phase 是本次请求阶段，不写入任务 stage。简短阶段可能在下一次查询前结束，页面允许直接显示已确认的后续阶段；不得为动画而延迟任务启动。

## 4. 统一服务顺序与事务边界

建议在服务层提供统一就绪函数，由回执启动协调服务调用；最终模块名可遵循项目现有结构。规则必须一致：

1. 参数和权限先检查，容量/启动占用按 14 获取。父恢复先判断是真正恢复浏览器执行，还是仅解除父级控制/处理 child 终态决策；后者沿用原语义，不进行无关登录检查。
2. 在事务外读取浏览器和目标页状态。首次/独立详情缺失时打开一次；`start_browser(wait_login=False)`，不等待用户人工登录。打开后重新检查目标可用性。
3. 调一次结构化 `check_login_state`，保留 available/unauthenticated/restricted/empty/response_error 及 URL 原因。手动布尔包装可复用它，但启动判断不能丢失分类。
4. 形成仅本次服务调用内可用的就绪结果，绑定 operation、目标模式/target 和执行进程；不可由客户端传 `skip_login`、`ready=true` 绕过检查。嵌套调用 `_start_new_batch` 时复用；下一个独立用户意图重新检查。
5. 探测完成后在短事务内重验 owner、任务版本、父控制权、容量和原 target 约束。期间 stop、current 切换、父权限变化均使旧启动意图失效，不允许旧检查成功覆盖新状态。
6. 保留既有父子原子变更与启动容量保证；检查失败发生在父子 running 变更之前。数据库事务中不得调用 CDP、网络或等待人工操作。
7. 对原任务恢复，真正采集的阶段从活跃 Pipeline operation/原执行器决定，不能只取 current_batch_id。提交后的启动异常按 14 回执与既有 interrupted/failed 路径处理，绝不宣称“未创建”或盲目回写旧快照。

检查必须有整个调用的有限 deadline；CDP 连接、页面创建、导航、25 秒样本等待和清理均分配预算，单个步骤不能反复重置总预算。具体数值按 01 的接口预算表记录；前端启动预算应覆盖后端 deadline 与正常传输余量。

## 5. 页面恢复与原页续采的区别

| 操作 | 页面丢失时行为 |
| --- | --- |
| 首次列表采集 | 可启动浏览器/打开合适页面，探测后新建任务 |
| 手动/历史/正式 JD 详情恢复 | 按详情采集原有机制准备详情页，使用保留的岗位身份；不伪造列表游标 |
| 原页继续列表、列表暂停恢复 | 必须核对持有的 expected_target_id 仍存在且处于可复用搜索页；缺失/替换/离开搜索页则明确拒绝本次恢复 |

原页丢失不是“任意 BOSS 页面可用”能够修复的问题。就绪检查不得把新 target 替换进旧任务、重置游标后仍声称继续。返回明确分类（建议 `CAPTURE_PAGE_NOT_REUSABLE`），保留已有结果与身份，给出重新采集入口；新采集属于新的用户意图。

保留已有有效搜索页。浏览器状态若只返回缓存的登录页而遗漏其他有效搜索页，需要在目标选择函数中检查真实候选和域名；不能以任意旧登录标签直接判定本轮未登录。

## 6. 登录分类与页面 URL

| 实时结果 | 启动行为 | 页面提示 |
| --- | --- | --- |
| available | 继续；仍需提交前状态重验 | 登录检查通过 |
| unauthenticated | 明确拒绝，无新任务 | BOSS 尚未登录，请登录后重新开始 |
| 本轮探测/实际目标跳转 `/web/user/` | 校验 BOSS 域名和路径后拒绝 | BOSS 尚未登录 |
| restricted | 拒绝，保留浏览器 | BOSS 访问受限，请处理页面验证 |
| empty | 不启动 | 样本为空，暂时无法确认登录状态 |
| response_error / deadline 超时 | 显示具体类别；回执按实际副作用确认 | 登录检查未完成/响应异常 |
| 浏览器/页面打开失败 | 拒绝，提供可操作原因 | 无法打开浏览器或目标页面 |
| 原页不可复用 | 拒绝本次续采/列表恢复 | 原搜索页已关闭或被替换，无法续采 |

URL 只针对本轮探测或准备采集目标；临时探测页关闭前记录最终 URL。旧登录标签继续打开不影响本轮有效探测判断。浏览器保留供人工登录，前端不等待人工完成，也不自动再次提交。

## 7. 验收

对应 `ST-01～ST-11、OP-01～OP-06`：

- 全入口矩阵逐行有对应用例；无权限/参数无效/容量冲突不会打开浏览器或推进采集。
- 同一 operation 嵌套调用与重复提交只进行一次探测；新用户意图按实际需要重新检查。
- 父恢复检查失败保留父子可恢复状态；检查中被 stop 的任务不会复活。
- 原页丢失时新页面不能让续采“成功”；历史结果保持可查看。
- 超时释放网络 loading，启动结果未知时仍可查询且不会重复创建。
- 自动接续和 pause/stop 不增加无关登录探测；实际运行中的风控/登录失效沿用现有处理。
