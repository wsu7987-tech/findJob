# 13 / 智能列表、正式 JD 与预取详情进度契约

文档修订：2026-09-26-r1。本次必需任务，解决“共享完整快照仍无法获得正式 JD 真实进度”的缺口。本文定义待实现契约，不表示接口已存在。

## 1. 基线事实与修改边界

- `smart_captures.get_smart_capture` 按 `current_batch_id` 读取列表执行器，并用其数据覆盖 `progress`。
- 正式 JD 位于 `fj_workflow_tasks`，`task_type = deep_job_search_jd`，`payload_json.jd_batch_id` 区分批次。
- 预取详情位于 `fj_workflow_prefetch_items`，通过 `prefetch_batch_id` 归组；已有 `get_prefetch_summary` 可复用。
- `process_detail_task_update` 对 queued/running 直接返回；正式 JD 的单项完成也未像预取一样逐项触发 `_touch_pipeline_snapshot`。
- 正式 JD、预取详情使用独立执行器，不应读取列表批次的 `details_completed` 冒充它们的进度。

修改 `smart_capture_engine.py`、`smart_captures.py`、相关响应/前端类型及页面映射。复用现有任务表、批次 ID 和发布函数，不引入新采集状态枚举、增量事件协议或详情进度表。

## 2. 新增快照字段

在 current GET、detail GET 与两类 SSE 的完整快照中统一增加 `collection_progress`，保留旧 `progress` 字段以兼容既有调用方。所有字段为本轮待实现，不得按“已有字段”直接调用。

| 字段 | 类型与语义 |
| --- | --- |
| `collection_progress.schema_version` | 固定为 1，表示本字段的数据形状 |
| `collection_progress.list` | 列表阶段摘要，未建立对应批次时为 null |
| `collection_progress.formal_jd` | 当前正式 JD 批次摘要，无批次时为 null |
| `collection_progress.prefetch` | 当前预取批次摘要，无批次时为 null |

每个非 null 摘要包含：

| 字段 | 定义 |
| --- | --- |
| `scope_id` | 列表执行批次 ID、`jd_batch_id` 或 `prefetch_batch_id`；只在同一 scope 内比较计数 |
| `unit` | 列表为 `page`，详情为 `job` |
| `stage` | 真实阶段/生命周期，沿用该来源的既有语义 |
| `total` | 当前 scope 已确定的计划总量；不能可靠确定时为 null |
| `processed` | 已处理数量；详情等于 `succeeded + failed`，不包括待处理和执行中 |
| `succeeded` / `failed` | 详情成功/失败数；列表无法独立计数时为 null |
| `pending` / `running` / `cancelled` | 详情尚未处理/执行中/取消数；不适用的列表字段为 null |
| `active_job` | 可选 `{id, title}`；缺失则为 null，不扫描其他任务或用上批岗位填充 |

这些是展示摘要，不替代任务 status、capabilities 或父子控制事实。暂停、停止和中断不会把未处理项记为失败。

## 3. 数据归属和聚合规则

### 列表

- scope 来自当前搜索执行批次，进度按本批请求深度及实际加载页数计算。
- 注意原采集器在 `list_completed` 时可能把 `progress_current/progress_total` 改写为岗位数；不能始终把这两个字段当作页数。
- 继续列表是新的阶段执行。保存/使用该阶段开始时的累计页数基线，显示“本次追加页数 / 本次计划页数”，累计页数另列；不得用累计页数除以本次深度。
- 有可证明的同单位分子、分母才显示百分比；否则 `total = null`，只显示已有计数。搜索提前耗尽可显示阶段完成标记，不伪造计划页数已全部执行。

### 正式 JD

- 以当前 Smart Capture 为 owner，再按 `payload_json.jd_batch_id` 分组，不能合并历史所有 JD 为本批进度。
- 优先选择含 pending/running 的当前批次；没有活动批次时保留最近批次摘要。最近批次按创建时间及稳定 ID 排序；发现多个活动批次时显式记录一致性问题，不相加冒充一个批次。
- `total` 为该批实际创建的 JD 任务数；`succeeded`、`failed`、`pending`、`running` 来自对应任务状态，`skipped/cancelled` 计入取消类，保留总量，不补为成功。
- 已存在详情而跳过网络采集的任务，在既有引擎确认 succeeded 后计入成功；不能只凭页面存在详情就提前计数。

### 预取详情

- 复用现有批次和 item 聚合，以 `prefetch_batch_id` 限定来源。
- `total` 使用该批实际创建的 item 数；`target_count` 是配置目标，不直接充当百分比分母。
- 区分 pending、collecting/running、ready、failed 及 cancelled；ready/promoted 的计数须保留详情成功事实，不能因生命周期提升而倒退。
- 分析和预取可并行：主状态由 Smart Capture 业务状态决定，预取放在智能次级区域，不创建第二套全局主进度条。

## 4. 推送与版本

1. 正式 JD 批次创建、单元启动、单元成功/失败、暂停/恢复/中断时，刷新所属 scope 的摘要。
2. 在更新任务状态的短事务内同步推进该 Smart Capture 的 `state_version`；事务提交后统一发布完整快照。复用既有版本/发布入口，避免同一次事实重复加版本或在事务中构造快照。
3. queued/running 回调不再无条件丢弃有展示意义的状态；只在摘要发生实际变化时发布。重复回调不重复计数。
4. 自定义详情仍按其执行器计数；正式 JD 和预取不能改写 `current_batch_id` 为单个详情任务，以免破坏列表续采、父子控制和历史查询。
5. 终态后的迟到详情回调不修改业务终态；重复事件和旧版本由共享 Store 丢弃。暂停后的真实已完成结果按既有引擎语义保存，不能冒充新一轮执行。
6. linked 与 independent 使用同一聚合函数；独立任务不得依赖 `workflow_run` 才能显示详情进度。

## 5. 前端映射

| 情况 | 取值与展示 |
| --- | --- |
| 搜索/列表执行 | 使用 `collection_progress.list` |
| `collecting_jd` | 使用 `formal_jd`，分别显示已处理、成功、失败 |
| 等待/进行分析并存在预取 | 主状态为分析，次级区域显示 `prefetch` |
| 更换 scope | 明确切换批次，清理旧 scope 的百分比，不比较不同批次版本或计数 |
| 新字段缺失/来源无法确定 | 保留业务阶段；标为进度暂不可用，隐藏百分比，不回退使用列表详情数 |
| 停止、失败、暂停、中断 | 保留真实计数和原因，不补为 100% |

百分比只在 `total > 0`、scope 一致且计数已确认时计算。空批次不显示 `0/0` 百分比；界面仍区分“无详情任务”与“进度读取失败”。

## 6. 验收

新增 `PG-01～PG-05`，并落实 `UI-04～UI-06、RT-02`：

- independent 正式 JD 三项任务，依次成功一项、失败一项、第三项执行中时，显示已处理 2、成功 1、失败 1、总量 3；每次变化由 detail SSE 可见。
- 同时存在列表、正式 JD 和预取时，三个摘要的 scope 与分母不串用。
- 旧批次成功数不进入新批次；已缓存 JD 成功按真实任务状态计入。
- 列表完成时不会把岗位数标为页数；继续列表不会用累计页数除本次深度。
- 暂停/停止/异常不会填满进度，重复回调不重复计数，终态不被晚回调改写。

验证优先使用现有服务与组件替身；本文件不包含任何已通过的运行结果。
