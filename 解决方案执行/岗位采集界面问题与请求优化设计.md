# 岗位采集界面问题与请求优化设计

## 1. 文档目的

本文重新梳理岗位采集页面当前存在的问题，并给出对应的界面与请求优化思路。

文档按问题拆分。每个问题分别描述：

- 当前表现；
- 代码中的触发链路；
- 对页面和用户的影响；
- 可选优化方案；
- 需要审阅的取舍。

本文只记录问题、请求链路、界面方案、请求优化方案和审阅事项，不设置实施优先级。所有方案均作为审阅材料。

## 2. 分析范围与依据

本次分析覆盖以下当前实现：

- 应用入口 `App.vue`；
- 岗位采集页面 `BossCapture.vue`；
- BOSS 采集、策略、平台会话和 Workflow Run Store；
- 全局 Smart Capture Codex 控制器；
- Smart Capture、Workflow Run、Context 和 Analysis 后端接口。

请求数量来自当前代码调用链推导。实际 Network 记录会受到以下条件影响：

- 是首次启动应用，还是应用内切换路由；
- 是否存在 current Smart Capture；
- current 是否为运行态、等待态或终态；
- 是否关联父 Workflow Run；
- 是否进入 `waiting_codex`；
- 桌面执行器心跳是否成功；
- 是否存在活动自定义采集任务；
- EventSource 的自动重连次数。

因此文档列出确定的触发关系，不把某个固定请求总数当成所有场景的共同结果。

## 3. 进入岗位采集页面时发出了什么请求

### 3.1 请求来源不是一个

进入岗位采集页面时，Network 中的请求来自五条链路：

1. 应用启动时的全局能力探测；
2. 应用启动时的全局 Smart Capture Codex 控制器；
3. 岗位采集页面自己的初始化；
4. current Smart Capture 恢复后追加的 Context、Analysis 和父任务请求；
5. 活动自定义采集任务的定时轮询。

如果只检查 `BossCapture.vue`，会漏掉应用入口和全局控制器产生的请求。

### 3.2 应用启动产生的 REST 请求

| 发起者 | 请求 | 触发条件 | 请求作用 | 返回后影响 | 优化思路 |
| --- | --- | --- | --- | --- | --- |
| `App.vue → configStore` | GET `/api/config` | 每次应用根组件挂载 | 读取生成能力配置，决定检查 Codex CLI 还是 LLM | 更新全局配置及能力状态 | 与页面自己的 GET config 统一数据所有权，避免同次启动重复读取 |
| `configStore` | POST `/api/config/check-codex` | `reasoning_executor=codex-cli` | 检查 Codex CLI 可用性、登录状态和推理配置 | 更新全局 Codex 能力提示 | 评估是否必须在应用启动时执行；可按功能入口或缓存时效触发 |
| `configStore` | POST `/api/config/check-llm` | 推理执行器不是 Codex CLI | 检查 LLM 连通性 | 更新全局 LLM 能力提示 | 与 check-codex 二选一，仍需审阅全局启动探测的必要性 |
| `configStore` | POST `/api/config/check-embedding` | 配置读取成功 | 检查 Embedding 连通性 | 更新全局 Embedding 能力提示 | 岗位采集首屏没有直接使用该结果，可与页面首屏解耦 |
| `App.vue → executorStore` | POST `/api/fine-job/boss-executor/desktop-heartbeat-test` | 每次应用根组件挂载 | 检查桌面执行器/插件连接 | 更新全局执行器面板 | 明确它属于应用级初始化，不应计入岗位采集页面完成加载的条件 |
| `executorStore` | POST `/api/fine-job/boss-executor/pairing-code` | 心跳失败 | 生成新的插件配对码 | 更新全局配对入口 | 保留条件触发；避免其失败影响岗位采集主体 |

### 3.3 岗位采集页面固定发出的 REST 请求

`BossCapture.vue` 挂载后并发启动以下请求：

| 发起者 | 请求 | 请求作用 | 返回后更新的页面区域 | 当前问题 | 优化思路 |
| --- | --- | --- | --- | --- | --- |
| `captureStore.loadStatus` | GET `/api/fine-job/boss-capture/status` | 获取专用浏览器是否运行、当前 URL、是否位于搜索页 | 顶部浏览器状态、浏览器操作按钮、采集前置条件 | 与其他初始化请求一起完成后页面才继续设置默认值 | 保留独立模块加载；浏览器状态失败不阻塞任务结果展示 |
| `captureStore.loadCities` | GET `/api/fine-job/boss-capture/cities` | 获取 BOSS 城市选项 | 自定义采集与智能采集城市选择 | 每次进入页面重新请求，结果通常相对稳定 | 评估 Store 会话级复用，并定义刷新入口与失效时机 |
| `strategiesStore.load` | GET `/api/fine-job/strategies/filters` | 获取岗位筛选策略、搜索词和城市范围 | 两种采集表单的筛选策略和默认值 | 每次进页重新请求；返回后会重设表单默认选择 | 将“展示已有任务”和“创建新任务”分开后，只在创建区需要完整策略 |
| `strategiesStore.load` | GET `/api/fine-job/strategies/recommendations` | 获取推荐策略 | 智能采集配置和分析配置 | 与筛选策略并发，但仍会改变表单内容 | 与筛选策略采用相同的数据复用和失效规则 |
| `platformStore.load` | GET `/api/fine-job/platform-sessions` | 获取 BOSS 平台登录会话 | 登录状态与登录操作 | 与浏览器 status 表达相近但来源不同 | 明确“浏览器进程状态”和“平台登录状态”的展示关系；独立加载 |
| `refreshCurrentSmartCapture` | GET `/api/fine-job/smart-captures/current` | 根据持久化 current 指针恢复最近一次 Smart Capture | 当前任务、岗位、批次、搜索组合、父任务等多个区域 | 返回的是完整任务快照，随后多条 SSE 还会再次发送完整快照 | 先明确 current 是“轻量指针”还是“首屏完整快照”，避免两种职责同时存在 |
| 页面配置初始化 | GET `/api/config` | 获取 Codex 模型、推理强度等表单默认值 | 智能采集配置表单 | 与应用启动的 GET config 重复 | 复用 configStore 已加载的数据；配置所有权保持唯一 |
| 页面配置初始化 | POST `/api/config/codex-models` | 调用配置中的 CLI 路径读取可选模型 | 模型选择控件 | 可能调用 Codex CLI；即使用户只查看历史结果也会执行 | 按界面需求触发，并评估模型目录缓存及刷新方式 |

页面固定请求中，`strategiesStore.load` 实际包含两个并行请求。因此仅页面初始化就会产生 8 个 REST 请求。

### 3.4 恢复 current 后追加的 REST 请求

只要 GET current 或 current SSE 返回了任务，页面还会根据任务内容继续请求：

| 发起者 | 请求 | 触发条件 | 请求作用 | 返回后更新 | 当前成本与问题 | 优化思路 |
| --- | --- | --- | --- | --- | --- | --- |
| `applyCurrentSmartCapture` | GET `/api/fine-job/smart-captures/{id}/context-snapshot?channel=...` | current 身份或语义状态发生变化 | 获取 Context 内容、预算和阻断状态 | Context 折叠区 | 页面没有展开 Context 时也会请求；后端在快照不存在时会创建或更新数据库记录 | 明确 Context 是运行必需数据还是检查工具；若只用于查看，可由对应区域触发 |
| `applyCurrentSmartCapture` | GET `/api/fine-job/smart-captures/{id}/analysis-items` | 与 Context 相同 | 获取分析任务、结果、反馈和 handoff 状态 | 分析队列、结果、Codex 状态 | 后端先构建完整 Smart Capture，再查询任务、岗位发现和反馈表 | 按页面实际展示层级决定首屏摘要与完整列表的边界 |
| `applyCurrentSmartCapture` | GET `/api/fine-job/workflow-runs/{id}` | capture 有父任务 ID，但完整快照中没有嵌入父任务 | 补取关联父任务 | 父任务镜像和操作区 | current 快照通常已携带父任务，这是一条回退请求 | 保留回退能力；主路径避免重复读取 |
| 全局 Codex 控制器 | GET `/api/fine-job/smart-captures/{id}` | 任务进入 `waiting_codex` 且需要自动交接 | 组成分析交接快照 | 不直接渲染页面，用于自动 Codex 交接 | 与页面和 SSE 中已有完整快照再次重叠 | 为自动交接提供专用轻量接口，或复用统一 Store 中的可信快照 |
| 全局 Codex 控制器 | GET `/api/fine-job/smart-captures/{id}/analysis-items` | 与上一项同时 | 获取待交接分析批次 | 启动 Codex 分析 | 页面也可能同时请求相同 Analysis Items | 统一 Analysis 数据所有权，避免页面与控制器各自读取 |

### 3.5 长连接与持续请求

| 发起者 | 连接/请求 | 作用 | 当前行为 | 优化思路 |
| --- | --- | --- | --- | --- |
| 全局 Codex 控制器 | SSE `/api/fine-job/smart-captures/current/events` | 全局监听 current 身份变化 | 应用存活期间保持连接；服务端首帧发送完整 current 快照 | 与页面 current SSE 合并所有权 |
| 全局 Codex 控制器 | SSE `/api/fine-job/smart-captures/{id}/events` | 监听活动任务是否进入 Codex 交接阶段 | 非终态任务建立；终态时关闭 | 与页面 detail SSE 订阅同一任务 |
| 岗位采集页面 | SSE `/api/fine-job/smart-captures/current/events` | 页面监听 current 切换 | 页面挂载后建立；服务端首帧发送完整 current 快照 | 与全局 current SSE 重复 |
| 岗位采集页面 | SSE `/api/fine-job/smart-captures/{id}/events` | 实时更新任务详情 | 当前实现只要存在 current 就建立，包括终态任务 | 需要按任务生命周期定义订阅规则，并与全局控制器统一 |
| Workflow Run Store | SSE `/api/fine-job/workflow-runs/{id}/events` | 更新关联父任务 | 非终态父任务建立；服务端首帧发送父任务完整快照 | 明确父镜像在岗位采集页需要的字段，评估摘要事件 |
| BOSS Capture Store | GET `/api/fine-job/boss-capture/tasks/{task_id}` | 更新活动自定义采集进度 | 首次约 0.5 秒，之后约每 1 秒；完成或失败后停止 | 评估事件推送、页面可见性控制或更合理的刷新节奏 |

### 3.6 从代码推导出的典型请求组成

#### 首次启动应用并直接进入岗位采集

基础 REST 请求：

- 应用级：GET config、生成能力检查、Embedding 检查、执行器心跳，共 4 个；
- 页面级：浏览器状态、城市、两类策略、平台会话、current、GET config、Codex models，共 8 个；
- 存在 current：Context 和 Analysis Items，再增加 2 个。

常见组合为 12 个基础 REST 请求；存在 current 时为 14 个。心跳失败、父任务回退读取或 `waiting_codex` 自动交接会继续增加请求。

#### 应用已经打开，仅切换到岗位采集

应用级能力探测通常不会重新执行，但页面级 8 个请求仍会重新触发；存在 current 时继续追加 Context 和 Analysis Items。

#### 实时连接

- 无 current：全局和页面各有一条 current SSE；
- 活动独立任务：两条 current SSE，加上全局和页面各一条 detail SSE；
- 活动关联任务：在上一项基础上再增加一条 Workflow SSE；
- 终态任务：全局控制器不会保留 detail SSE，但页面仍会建立 detail SSE。

以上数量不包含 EventSource 断线后的自动重连。

### 3.7 重复的完整快照构建

`GET /smart-captures/current` 返回的不是轻量 current 指针，而是完整 Smart Capture 快照。完整快照会读取或组合：

- Smart Capture 主记录；
- 全部批次；
- 批次岗位快照；
- 当前内存采集任务；
- 搜索组合；
- Candidate Pool；
- Prefetch 摘要；
- 岗位列表；
- 关联父 Workflow Run。

活动任务进入页面时，同一份完整快照可能通过以下路径重复构建和传输：

1. 页面 GET current；
2. 全局 current SSE 首帧；
3. 页面 current SSE 首帧；
4. 全局 detail SSE 首帧；
5. 页面 detail SSE 首帧。

此外：

- Context 接口内部会先调用 `get_smart_capture`；
- Analysis Items 接口内部也会先调用 `get_smart_capture`；
- `waiting_codex` 自动交接还会再读取 Smart Capture 和 Analysis Items。

因此 Network 中看似不同的 URL，后端内部仍可能重复构建相同的大快照。这是页面进入慢和后端重复工作的主要候选原因。

### 3.8 请求的缓存、按需加载与实时更新分类

岗位采集页面的请求不能统一套用一种缓存方式。根据数据变化频率和业务用途，可分为三类。

#### A. 适合由 Store 复用的数据

| 请求 | 当前状态 | 建议的 Store 行为 | 刷新或失效条件 |
| --- | --- | --- | --- |
| GET `/api/fine-job/boss-capture/cities` | 数据已写入 `captureStore.cities`，但 `loadCities` 每次调用仍会请求 | 增加已加载状态和进行中请求复用；当前应用会话内已有数据时直接使用 | 用户主动刷新；后端明确提供城市数据版本变化通知 |
| GET `/api/fine-job/strategies/filters` | 数据保存在 `strategiesStore.filters`，页面挂载仍调用 `load` | Store 已加载时复用；多个组件同时请求时复用同一个进行中任务 | 策略创建、保存、删除、AI Change Set 应用成功后失效或立即更新 |
| GET `/api/fine-job/strategies/recommendations` | 与筛选策略一起每次重新加载 | 与筛选策略采用同一加载状态和并发合并机制 | 推荐策略创建、保存、删除、AI Change Set 应用成功后失效或立即更新 |
| GET `/api/config` | 应用启动和岗位采集页面分别读取 | 统一由 `configStore` 持有；页面读取 Store，不再独立调用 | 配置保存成功后用返回结果更新 Store；用户主动重新加载 |
| GET `/api/fine-job/platform-sessions` | 保存在 `platformStore`，进入页面仍重新请求 | 在当前会话短期复用；环境状态区域可以独立刷新 | 打开登录窗口、登录检测、保存会话或退出登录后更新 |
| POST `/api/config/codex-models` | LocalStorage 只在接口失败时兜底，正常进入页面仍会调用接口 | 由全局配置 Store 按 `codex_cli_path` 保存模型列表和加载状态；相同路径复用数据与进行中请求 | CLI 路径变化、用户主动刷新模型目录、缓存为空或上次加载失败后重试 |

Store 需要同时保存：

- `hasLoaded`：区分“尚未加载”和“已加载但结果为空”；
- `loading`：供界面显示模块级加载状态；
- 进行中的请求对象：避免多个组件同时发起同一请求；
- `error`：错误只归属对应数据模块；
- `loadedAt`：供后续审阅是否需要时效刷新；
- `forceReload` 入口：支持明确的用户刷新和业务失效。

城市、策略、配置和模型列表的变化特征不同，失效条件应分别定义。会话级复用不等于长期持久化。

#### B. 适合按界面区域加载的数据

| 请求 | 当前状态 | 建议触发方式 | 需要保留的行为 |
| --- | --- | --- | --- |
| GET `/api/fine-job/smart-captures/{id}/context-snapshot` | 恢复 current 后自动请求 | 用户打开当前任务 Context 区域时加载 | Channel 或任务 ID 变化后读取对应数据；明确区分读取与创建 |
| GET `/api/fine-job/smart-captures/{id}/analysis-items` | 恢复 current 后自动请求 | 打开分析结果区域时加载；任务摘要只使用轻量计数 | 分析版本变化后标记失效，用户查看时刷新 |
| GET `/api/fine-job/workflow-runs/{id}/context-snapshot` | 查看历史 Run 时读取 | 保持历史查看操作触发 | 当前任务 Context 与历史 Run Context 分别管理 |
| POST `/api/config/codex-models` | 页面挂载即调用 | 用户进入创建配置并使用模型控件时确保数据可用 | 缓存结果先展示，刷新过程不清空已有选项 |
| GET `/api/fine-job/boss-capture/cities` | 页面挂载即调用 | 创建采集区域需要城市选择时确保数据可用 | Store 已加载时直接展示 |

按需加载需要稳定的占位区域和模块级加载状态，避免用户打开区域后页面整体移动。

#### C. 需要实时性，不适合普通缓存的数据

| 请求或连接 | 数据特征 | 建议方式 |
| --- | --- | --- |
| GET `/api/fine-job/boss-capture/status` | 浏览器进程和当前页面可能随时变化 | 进入相关页面时刷新，或由共享状态通道更新；Store 只保存最后状态，不把它当长期缓存 |
| GET/SSE `/api/fine-job/smart-captures/current` | current 身份会随任务创建而变化 | 使用唯一全局 Store 和唯一 current 数据源；页面消费 Store |
| SSE `/api/fine-job/smart-captures/{id}/events` | 活动任务进度持续变化 | 每个活动任务只保留一个详情订阅；终态订阅策略单独审阅 |
| SSE `/api/fine-job/workflow-runs/{id}/events` | 活动父任务状态持续变化 | 按活动父任务 ID 共享订阅；业务状态与订阅状态分开 |
| GET `/api/fine-job/boss-capture/tasks/{task_id}` | 自定义任务进度持续变化 | 使用事件流，或采用可见性和阶段感知的轮询策略 |
| POST `/api/fine-job/boss-executor/desktop-heartbeat-test` | 执行器连接状态 | 归属应用级连接管理，不由岗位采集页面重复触发 |

#### D. 进入页面时的建议调用关系

```text
进入岗位采集页面
  ├─ 从统一 Store 读取 current 和最后已知环境状态
  ├─ 当前/最近任务存在
  │    ├─ 先展示任务摘要和已有结果
  │    ├─ 活动任务接入统一实时订阅
  │    └─ Context、完整 Analysis、历史工具按区域加载
  └─ 用户进入创建采集
       ├─ 城市 Store 已加载则直接使用
       ├─ 策略 Store 已加载则直接使用
       ├─ 配置直接读取 configStore
       └─ 模型 Store 有当前 CLI 路径的数据则直接使用
```

这种分类的目标是减少路由进入时的固定请求，同时保留环境状态、当前任务和活动进度所需的实时性。

## 4. 问题一：请求所有权重复

### 当前表现

应用级控制器和岗位采集页面分别建立 current SSE、detail SSE，并各自消费完整 Smart Capture 快照。页面还额外执行 GET current。

### 页面影响

- 同一任务可能被连续应用多次；
- current、Context、Analysis、父任务区域在不同时间刷新；
- 用户看到页面在进入后的数秒内持续变化；
- 网络面板中存在功能相同的长连接。

### 优化方案

需要在两种架构中选择一种：

#### 方案 A：全局 Store 统一持有实时连接

- 应用级控制器持有唯一 current SSE；
- current 非终态时持有唯一 detail SSE；
- 页面只读取 Store；
- 页面需要的 Context、Analysis 仍按模块读取；
- 跨页面的 Codex 自动交接和通知继续工作。

优点：保留跨页面能力，消除重复 SSE。  
代价：需要让全局控制器承担页面可消费的完整状态，并处理页面订阅生命周期。

#### 方案 B：页面持有实时连接

- 全局控制器不常驻订阅；
- 进入岗位采集或需要 Codex 自动交接时才建立连接；
- 离开页面后关闭。

优点：生命周期直观。  
代价：离开岗位采集页后，自动交接和跨页面状态提示需要新的触发机制。

### 待审阅事项

- 离开岗位采集页后是否仍必须自动触发 Codex 交接；
- 是否需要在其他页面显示岗位采集实时状态；
- Store 中应保存完整快照还是轻量摘要。

---

## 5. 问题二：current 接口与 SSE 首帧都承载完整快照

### 当前表现

current 在概念上用于确定“当前任务是谁”，实际返回完整任务数据。current SSE 和 detail SSE 的首帧也都是完整快照。

### 页面影响

- 首屏恢复方便，但相同数据被多次传输；
- 岗位数量和批次增长后，进入页面成本继续上升；
- current 身份变化与详情进度变化无法采用不同刷新粒度。

### 优化方案

#### 方案 A：保留 GET current 作为完整首屏快照

- 页面首次只通过 GET current 获取完整快照；
- current SSE 只发送 ID、状态和版本；
- detail SSE 只发送后续变化；
- 建立 detail SSE 时不再发送相同首帧，或允许客户端携带已知版本。

#### 方案 B：current 只返回轻量摘要

摘要包含：

- `smart_capture_id`；
- `status`、`stage`；
- `state_version`；
- `workflow_run_id`；
- 关键计数；
- 开始和结束时间；
- 等待或结束原因。

岗位、批次、搜索组合、候选池、分析和父任务按模块加载。

方案 B 的长期收益更高，接口和页面改动也更大。

### 待审阅事项

- 首屏必须一次拿到哪些字段；
- 岗位结果是否独立分页；
- SSE 采用完整快照、摘要快照还是差量事件；
- 旧客户端兼容方式。

---

## 6. 问题三：页面初始化加载了当前界面暂时不需要的数据

### 当前表现

页面无条件加载城市、两类策略、平台会话、应用配置和 Codex 模型。用户进入页面查看已完成任务结果时，这些数据仍会加载。

### 页面影响

- 查看结果和创建任务共享同一初始化成本；
- 模型列表调用 CLI，响应时间可能明显长于普通数据库查询；
- 策略返回后会重新设置表单默认值，引起界面内容变化。

### 界面优化方案

将页面内容分成两个清晰入口：

- 查看当前/最近任务：优先显示任务状态和结果；
- 配置新采集：用户进入配置区域后再准备城市、策略、模型等选项。

这两个入口如何呈现需要审阅，可以采用独立页面、页签、抽屉或同页切换。

### 请求优化方案

- 浏览器状态和 current 作为页面基础数据；
- 平台会话由环境状态区域独立加载；
- 城市和策略由创建配置区域触发；
- GET config 复用全局 configStore；
- Codex models 由模型控件触发，并提供明确刷新入口；
- Store 复用必须定义策略修改、配置保存后的失效规则。

---

## 7. 问题四：Context 和 Analysis 在恢复任务时自动加载

### 当前表现

current 身份、状态、阶段、当前批次或等待原因变化时，页面并行请求 Context 和 Analysis Items。

### 特别风险

Context GET 在没有现成快照时会创建或更新数据库快照。它不仅是显示层读取。

Analysis Items 会先构建完整 Smart Capture，再查询分析任务、岗位发现和反馈。

### 页面影响

- 用户没有展开 Context，也会产生请求和数据库写入；
- 运行阶段变化可能触发两个重接口；
- 分析区和 Context 区随后出现或变化，扩大页面抖动。

### 优化方案

可按数据用途分层：

- 任务顶部只使用 current 摘要中的分析计数和 Context 状态；
- 展开 Context 时读取完整快照；
- 打开分析区域时读取 Analysis Items；
- Codex 自动交接使用专用 handoff snapshot，不依赖页面是否打开；
- 后端将“读取 Context”和“确保创建 Context”拆成语义明确的接口。

### 待审阅事项

- Context 是否属于用户查看工具，还是引擎运行必需状态；
- 终态结果页是否默认展示完整分析结果；
- 自动交接最少需要哪些 Analysis 字段。

---

## 8. 问题五：进入页面后布局持续变化

### 当前表现

请求并发启动后，各模块按返回顺序更新：

- 浏览器状态；
- 登录状态；
- 策略和表单默认值；
- current 任务；
- Context；
- Analysis；
- 父任务；
- Codex 模型。

页面当前由多个纵向区块组成，模块出现或内容增长会不断推动下方内容。

### 界面优化方案

建立一次明确的页面初始化阶段：

1. 确定浏览器状态是否可用；
2. 确定是否存在 current 及其状态；
3. 确定本次首先展示任务结果还是创建入口；
4. 渲染稳定的页面骨架；
5. 其他模块在固定容器内独立加载。

建议的稳定布局：

- 顶部环境条：浏览器、BOSS 登录、执行器；
- 当前任务摘要：任务 ID、统一状态、阶段、关键计数、允许操作；
- 主内容：岗位、分析、执行详情；
- 创建配置：作为独立入口；
- Context 和历史查询：放入高级工具区。

局部加载失败只更新对应模块，不替换整页内容。

## 9. 问题六：终态任务恢复后仍带有运行态行为

### 需求边界

终态岗位采集需要恢复，以便查看最终岗位、分析结果、执行批次、配置和父任务关系。

### 当前表现

- 页面只要存在 current 就建立 detail SSE，终态任务也会连接；
- 恢复关联父任务后，`setRun` 会识别终态并停止订阅，随后页面又调用 `startPolling`；
- `startPolling` 对终态不会真正建立 Workflow SSE，但会把 `pollingActive` 重新设为 true；
- 终态结果、创建表单、分析指导和运行控制相关内容仍位于同一区域。

### 页面影响

- “任务已经结束”和“仍处于活动同步状态”可能同时出现；
- 状态标识、按钮和提示依赖不同字段，容易产生矛盾；
- 用户难以判断当前看到的是历史结果还是可继续操作的任务。

### 优化方案

恢复终态时加载：

- 最终任务摘要；
- 岗位结果；
- 分析结果；
- 执行批次；
- 当时使用的只读配置；
- 父任务只读摘要。

运行态专属能力由统一状态模型控制：

- 实时详情订阅；
- 父任务实时订阅；
- 暂停、继续、停止；
- 当前动作和下一动作；
- 可编辑的运行参数。

终态是否继续监听 current 指针变化，需要与“新任务在其他页面创建后，本页是否自动切换”一起审阅。

## 10. 问题七：一个页面同时使用三套任务状态

### 当前状态源

| 状态源 | 数据 | 当前用途 |
| --- | --- | --- |
| `captureStore.task` | BOSS 批次/自定义采集任务 | 采集概览、进度、部分按钮 |
| `currentSmartCapture` | Smart Capture current 完整快照 | 智能采集详情、岗位、Planner、分析 |
| `workflowStore.currentRun` | 关联父 Workflow Run | 父任务状态与控制 |

### 当前问题

- 三套状态有不同生命周期和终态集合；
- “采集概览”主要读取 `captureStore.task`，智能任务详情读取 `currentSmartCapture`；
- 页面路由返回时 Store 中可能仍保留上一个任务；
- 父任务的 `status`、`control_state`、`pollingActive` 分别表达业务状态、控制状态和订阅状态；
- 如果界面把订阅状态当成任务状态，就会出现“active / 已结束 / 可暂停”等冲突。

### 优化方案

页面先确定展示对象：

- 当前 Smart Capture；
- 当前 Smart Capture 的活动批次；
- 关联父 Workflow Run；
- 活动自定义采集任务。

随后生成一个只供界面使用的统一视图模型：

- `task_kind`；
- `lifecycle_status`；
- `stage`；
- `is_terminal`；
- `can_pause`、`can_resume`、`can_stop`；
- `sync_state`；
- `terminal_reason`；
- `started_at`、`completed_at`。

顶部状态和操作区只读取该视图模型。各详情模块仍展示自己的领域数据，但不再各自解释主状态。

## 11. 问题八：终态结果和新采集配置混在同一界面

### 当前表现

终态 current 存在时：

- 顶部展示“最近任务结果”；
- 下方仍渲染完整智能采集配置表单；
- `smartCaptureCanStart` 允许再次开始；
- 配置摘要中还显示上一任务 Run ID；
- “本次智能采集分析指导”仍可编辑和保存。

### 页面影响

- 上一任务结果与下一任务配置没有明确边界；
- 用户无法确认表单值来自任务快照、系统默认值还是当前策略；
- 编辑分析指导可能被理解为修改新任务配置，也可能被理解为修改已结束任务。

### 界面优化方案

需要把两类内容明确分开：

#### 查看任务

- 展示任务状态、结果和只读执行配置；
- 展示岗位与分析结果；
- 终态不呈现运行控制；
- 是否允许对历史结果追加分析，使用独立操作表达。

#### 创建采集

- 展示可编辑配置；
- 配置来源明确标注为默认配置、已选模板或复制自某次任务；
- 创建成功后进入新任务详情；
- 上一次任务仍可通过历史入口查看。

具体采用路由、页签还是同页切换，需要结合现有导航审阅。

## 12. 问题九：状态和进度信息重复

### 当前表现

任务状态分散在：

- 页面顶部状态；
- 采集概览；
- Smart Capture 执行详情；
- 当前任务提醒；
- 父任务镜像；
- Search Planner；
- 采集进度；
- 驾驶舱。

### 页面影响

- 同一状态用不同文案重复表达；
- 更新时机不同会显示互相矛盾的信息；
- 真正重要的岗位和分析结果被推到页面下方；
- 终态仍可能显示“当前组合”“下一动作”等运行语义。

### 界面优化方案

- 顶部任务摘要承担主状态表达；
- 概览只保留关键指标；
- Search Planner 放入执行详情；
- 父任务区域只展示关系和父层状态；
- 终态使用最终范围、最终组合、结束原因和完成时间；
- 岗位与分析结果提升到主内容层级；
- 同一字段只选择一个权威来源。

## 13. 问题十：自定义采集使用每秒轮询

### 当前表现

活动自定义任务首次约 0.5 秒后请求一次详情，之后约每秒请求：

`GET /api/fine-job/boss-capture/tasks/{task_id}`

任务完成或失败、页面卸载时停止。

### 影响

- 任务持续时间越长，请求越多；
- 每次返回都会更新任务和进度区域；
- 与 Smart Capture SSE、Workflow SSE 同时存在时，Network 更难理解；
- 页面处于后台时仍保持相同刷新节奏。

### 优化方案

- 为自定义采集提供事件流；
- 或按照任务阶段采用不同刷新频率；
- 页面不可见时降低频率或暂停；
- 响应携带版本，版本未变化时减少前端状态提交；
- 自定义任务与 Smart Capture 的传输机制在界面上保持一致。

## 14. 问题十一：历史与 Context 检查工具占据主流程

### 当前表现

“历史 / Context 检查工具”位于当前任务详情和父任务区域之间，包含 Run ID 输入、Channel 切换和原始 JSON 展示。

### 页面影响

- 面向诊断的工具打断普通用户查看任务的路径；
- Context 切换会同时刷新当前任务和历史任务的 Context；
- 当前任务、父任务、历史 Run 三个身份容易混淆；
- 原始 JSON 占用较大页面空间。

### 界面优化方案

- 移入“高级工具”或“诊断”区域；
- 当前任务 Context 与历史 Run Context 分开；
- 历史任务使用独立的历史列表或按 ID 查看页面；
- 默认展示摘要，原始 JSON 由用户展开；
- Channel 切换只刷新当前正在查看的对象。

## 15. 问题十二：父任务入口与驾驶舱恢复范围不一致

### 当前表现

岗位采集可以恢复终态 Smart Capture，并显示其关联父任务。驾驶舱当前主要恢复非终态任务。终态结果中的“返回驾驶舱”没有携带指定 Run ID。

### 页面影响

用户从终态岗位采集跳转驾驶舱后，看到的可能不是对应父任务，或者看不到任何任务。

### 优化方案

可审阅以下两种方向：

- 驾驶舱支持按 Workflow Run ID 打开只读历史详情；
- 终态岗位采集只展示父任务摘要，并提供明确的历史查看入口。

普通“返回驾驶舱”用于当前活动任务，历史父任务使用带 Run ID 的入口，避免两个语义混用。

## 16. 建议的目标界面结构

### 16.1 顶部环境状态条

展示：

- 专用浏览器状态；
- BOSS 登录状态；
- 桌面执行器状态；
- 手动刷新或处理入口。

三类状态独立加载，任何一项失败都不阻止用户查看已有结果。

### 16.2 当前任务摘要

展示：

- 任务类型与任务 ID；
- 统一生命周期状态；
- 当前阶段或结束原因；
- 开始时间、完成时间；
- 岗位、候选和分析关键计数；
- 当前状态允许的操作。

这里是页面唯一的主状态表达。

### 16.3 主内容

建议按业务目标组织：

1. 岗位结果；
2. 分析结果；
3. 执行详情；
4. 父任务关系；
5. 高级工具。

岗位和分析是用户进入页面后最需要查看的内容，应位于配置、Planner 和原始 Context 之前。

### 16.4 创建采集

创建配置与任务结果建立明确边界。创建区域包含：

- 筛选策略；
- 搜索词和城市；
- 采集规模；
- 推荐策略与分析目标；
- Codex 模型；
- 执行策略；
- 配置来源说明。

是否默认复制上一次配置，需要产品审阅后确定。

## 17. 请求优化总体方案

### 17.1 第一层：明确请求所有权

- config 只由 configStore 加载；
- Smart Capture current/detail SSE 只由一个控制器持有；
- Workflow SSE 只服务于非终态父任务；
- 页面模块通过 Store 或明确的查询服务消费数据。

### 17.2 第二层：定义首屏最小数据

首屏只负责回答：

- 环境是否可用；
- 当前任务是谁；
- 当前任务处于什么状态；
- 用户首先应该看到结果还是创建入口。

城市、策略、模型、完整分析、Context 和历史工具按照界面区域加载。

### 17.3 第三层：拆分重快照

- current 摘要；
- 任务详情摘要；
- 岗位分页；
- 批次与 Planner；
- Analysis Items；
- Context；
- 父任务摘要。

拆分后需要避免产生大量细碎请求，可按页面区域组合接口。

### 17.4 第四层：定义数据失效规则

需要明确：

- 城市数据多久刷新；
- 策略保存后哪些页面立即失效；
- config 保存后模型列表是否刷新；
- current 切换时哪些模块清空；
- state_version 变化时刷新哪个模块；
- 终态结果是否保持不可变。

### 17.5 第五层：统一实时与轮询策略

- 活动 Smart Capture 使用一套 SSE；
- 活动父任务按需使用一套 Workflow SSE；
- 终态任务只保留 current 身份监听或静态读取；
- 自定义采集选择 SSE 或可控轮询；
- 页面不可见时定义连接保留策略。

## 18. 审阅重点

后续审阅需要对以下问题给出明确结论：

1. Smart Capture 实时连接由应用级控制器还是页面持有；
2. 离开岗位采集页后是否仍要自动执行 Codex 交接；
3. current 接口保留完整快照还是改为轻量摘要；
4. 终态页面是否监听 current 指针变化；
5. 查看已有任务与创建新采集采用何种界面关系；
6. 终态任务是否允许追加分析或修改分析指导；
7. Context 的读取与创建是否拆分；
8. 城市、策略、配置和模型列表的失效规则；
9. 自定义采集继续使用轮询还是增加事件流；
10. 驾驶舱是否支持按 Run ID 查看历史任务。

## 19. 后续验证记录要求

方案确认后，应分别记录以下场景的 Network：
