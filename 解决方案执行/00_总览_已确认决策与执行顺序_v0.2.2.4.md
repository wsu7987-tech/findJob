## 一、已确认决策 / 本轮主要完成事项（人工审阅区）

### 1. 父子层级与职责

```text
Workflow Run（驾驶舱父级编排）
└─ Child Task（通用子任务契约）
   └─ Smart Capture（当前首个 child：岗位采集域执行工作流）
      ├─ Search / Search Combination
      ├─ BOSS Capture Batch
      ├─ Candidate Pool
      ├─ JD Detail
      ├─ Analysis Batch
      ├─ Codex Handoff / Analysis
      ├─ Prefetch Batch / Item
      ├─ Candidate Reservation
      ├─ Context
      └─ Recommend / Review 结果
```

- Workflow Run 只编排 child，不直接拥有/执行岗位采集内部 BOSS/JD/Analysis/Prefetch 单元。
- Smart Capture 不是纯抓取器，是岗位采集域的完整执行工作流。
- 父层以后会编排更多 child，因此父层永久数据契约只依赖通用 `child_type/ref/status/result_summary/timestamps/capabilities`，不能永久写死 Smart Capture 私有字段。

### 2. 两个入口，共用一套 Smart Capture Engine

- 驾驶舱入口：父 Workflow Run + `source=task_cockpit` 的 linked Smart Capture。
- 岗位采集入口：`source=boss_capture`、`workflow_run_id=null` 的 independent Smart Capture。
- 两种 Smart Capture 必须共用同一 Candidate/JD/Analysis/Codex/Prefetch Engine。
- independent 不创建隐藏 Workflow Run，不控制任何驾驶舱父任务。

### 3. 唯一 Current Smart Capture 与采集执行容量是两个概念

#### Current Smart Capture slot

同一时刻最多一个非终态 Smart Capture 占用 current slot。至少：

`pending/running/pausing/paused/waiting_next_batch/waiting_for_user/interrupted`

都占槽。

linked pending 也必须创建后立即占槽，不等待 BOSS batch 真正启动。

#### Collection execution capacity

Smart Capture 与现有“自定义采集”共享实际 BOSS 采集执行容量：

- 非终态 Smart Capture 存在时，禁止新建/启动自定义采集；
- 自定义采集正在占用执行器时，禁止创建/启动 Smart Capture；
- 不能只看进程内 running batch；paused/pending Smart Capture 仍然拥有 Smart Capture current slot；
- 互斥必须由统一后端业务检查覆盖 BossCapture 自定义入口、驾驶舱 linked 入口、独立 Smart Capture 入口以及 Codex 触发自定义采集入口。

### 4. 岗位采集固定路由，不通过 ID 恢复 current

- 固定 `/fine-job/capture`；
- 驾驶舱跳转不携带 smart_capture/workflow_run id；
- 侧边栏和驾驶舱进入看到同一个服务端 current Smart Capture；
- current 身份不能由 `restoreLatest(false)`、route param、前端最近 Store 推断。

### 5. 投递目标决定自动生命周期完成路径

`delivery_target_enabled=false`：

```text
candidate_count >= candidate_target_count
→ Smart Capture completed
→ linked parent 消费结果并继续下一 child/完成
```

`delivery_target_enabled=true`：

```text
Candidate → JD → Codex Analysis + Prefetch
→ Recommend / Review 合约满足
→ Smart Capture completed
→ linked parent 继续
```

不得新增与此平行冲突的 `completion_goal`。

OFF completed 是生命周期终态：之后的 Manual Analysis/人工选岗位送 Codex 属于后处理能力，**不得把 completed Smart Capture 改回 running/waiting，不得重新阻塞已经推进的 parent，不得重复发 child-completed 事件。**

### 6. 现有 Pipeline 优化必须保真

必须保留：Search Combination、Candidate reservation、Analysis Batch、Manual Analysis Batch、Codex handoff/started ACK/retry/resubmit/re-handoff、Analysis N 与 Prefetch N+1 并行、ready prefetch promotion、Context snapshot/budget、Recommend/Review 目标判断、stop policy 等现有正确能力。

禁止通过全串行、删除 Prefetch/Reservation、隐藏创建 Workflow Run、砍历史 Context 等方式“简化迁移”。

### 7. 迁移期间只有一个执行 authority

这是 v0.2.1 的关键补充；v0.2.2.1 固定 child start，v0.2.2.2 补齐 completion/outcome Cutover gate，v0.2.2.3 进一步固定 linked-only outcome、child version guard 与 hard-failed 不复活；v0.2.2.4 确认 hard failure 后 parent 与 child stop 共享同一 skip/end 决策集合。

- Task 02～08B 期间，linked Smart Capture 可以先成为 child identity/owner bridge，但**不能让旧 Workflow Engine 和新 Smart Capture Engine 同时对同一 child 启动执行单元**。
- Task 04～08B 只建立 seam、schema、repository、domain API/transport 与可测试的新执行路径。
- **Task 09 是正式 Engine Cutover 点**：全部前置 characterization tests 通过后，且 **linked** Smart Capture 的最小 completion/outcome 闭环（terminal 判定 → 持久化 result summary → child outcome event → parent 幂等 + child version guard 消费）通过后，生产运行 authority 才能一次性切到 Smart Capture。Task 10 继续补齐完整 OFF/ON completion policy 与 OFF completed 后处理，不允许在 09→10 之间留下“新 authority 已切但 outcome 无法闭环”的状态。
- Cutover 后：父 Workflow 不得再直接启动 BOSS capture、JD、Analysis、Prefetch；旧 Workflow 执行 API 只保留历史/兼容桥所需的最小能力。
- 外部 BOSS/Codex side effect 不能发生在创建身份的 DB 事务中。

详见 `D_执行权切换与API调用链矩阵.md`。

### 8. 父子 pause / resume / cancel / failure

目标语义固定为：

- parent pause → parent `paused`，向 linked child 发安全 pause；
- child pause → child paused，parent **`waiting_child_paused`**（不是用户主动暂停整个父任务）；
- resume 只解除对应 cause，前端不得 `resume()` 后再猜测性 `advance()`；
- parent cancel → 父层执行 `cancel`，向 Smart Capture child 只发送 `stop`；Smart Capture 最终生命周期写 `stopped`，parent 写 `cancelled`；
- child stop → child lifecycle=`stopped`，parent `child_cancelled_waiting_decision`，由驾驶舱决定跳过 child/结束父任务；
- recoverable child interruption → parent `control_state=waiting_child_interrupted`，并返回明确 `waiting_reason`，不能用“等价 reason”替代 canonical control state，也不能自动推进；
- hard child failure → child `failed` terminal，parent `child_failed_waiting_decision`，不能静默 completed/cancelled/继续；同一 failed child 不允许 retry/recover；
- retry/resume 只属于 `interrupted`/其他明确非终态可恢复 reason；**（v0.2.2.4 已确认）** failed 后 parent 提供与 `child_cancelled_waiting_decision` 相同的决策集合：跳过该 child 继续后续编排 / 结束父任务，二选一；skip 不改变该 child 的 `failed` 终态，也不暴露 retry；不允许万能 `advance` 绕过卡点。

详见 `B_父子任务控制状态矩阵.md`。

### 9. 删除万能“立即推进”，保留合法卡点动作

删除岗位采集页通用人工 `立即推进` UI。

保留状态机内部 transition 以及明确动作：resume、retry 当前步骤、重试 interrupted、跳过已取消/已失败 child、结束父任务、返回驾驶舱处理等。

### 10. Workflow Run 区域最终拆成三类职责

1. **Smart Capture 业务详情**：Planner、Candidate、JD、Analysis、Prefetch、Codex、Recommend/Review、当前 Context；
2. **历史 / Context 检查工具**：保留 Workflow Run ID 输入、Context 类型下拉、历史 Run/Context 查看；
3. **当前 linked parent 镜像**：只由 `currentSmartCapture.workflow_run_id` 决定，只显示/控制真正父任务。

历史查看与当前父控制必须分状态源：

```text
currentSmartCapture
linkedParentWorkflowRun   # 可控制
inspectedHistoricalRun    # 只读
```

输入历史 Run B 不得改变 linked parent A、current Smart Capture、控制按钮目标、SSE/polling 控制对象。

### 11. Codex/Analysis 属于 Smart Capture Domain

独立 Smart Capture 也必须能完整运行 Codex。因此以下不能继续要求 `workflow_run_id` 才能执行：

- Analysis Item 列表/上下文/保存；
- Manual Analysis Batch；
- Current Context snapshot；
- Codex session attach；
- handoff claim / prompt-written / ACK started / release / retry；
- MCP FineJob tools；
- renderer handoff service 与 App-level auto controller；
- CodexWorkspace/terminal 的当前任务定位。

新运行链以 `smart_capture_id` 为业务 identity；linked 的 `workflow_run_id` 只作为父关联/历史兼容键。

### 12. 驾驶舱 UI

未运行或父真正终态：显示编排区。

- 子任务选择按集合建模：例如 `selectedChildren[] / childConfigs / childValidation`，即使 Phase 1 只有 Smart Capture，也不要写死一个永久 boolean。
- 勾选岗位采集 → 显示配置完整度 → 点按钮从右侧 Drawer 编辑共享表单。
- 所有已选择 child 配置有效才能开始。

父任务非终态：隐藏整个可编辑编排/表单区，只显示父状态、快递式时间线、合法操作和结果摘要。

`child_cancelled_waiting_decision` / `child_failed_waiting_decision` / interrupted 等等待态仍是非终态，不能重新出现新任务编排区。

岗位采集详情固定跳 `/fine-job/capture`，无 ID。

父真正终态后编排区重现，但上一轮 final result/timeline 仍保留，直到用户发起新任务。

### 13. 共享配置表单

驾驶舱 Drawer 与 BossCapture 复用表单组件/数据模型/校验规则，不复用 submit action。

- OFF：只要求候选采集路径实际所需字段；
- ON：才要求 recommendation/Codex/Recommend/Review/Analysis 等条件字段；
- 后端保留最终校验；
- 抽组件不允许丢字段或改变既有默认值/回显。

### 14. 页面保护边界

- `TaskCockpitNew.vue` **相关实现范围**可按目标重构，包括相关 component/store/type/service；不是限制只能修改一个单文件。
- 旧 `TaskCockpit.vue` 不修改、不复用。
- `BossCapture.vue` 高风险：迁移、抽组件、接线、归类优先；禁止为了“干净”删掉已有无关能力。
- Context 下拉、历史 Run ID、Planner、Candidate/JD、Analysis、Codex、Prefetch、历史结果、Manual Analysis 等除明确说明外全部保留。
- 当前明确允许删除的 UI 功能只有通用“立即推进”。

## 二、v0.2.2.4 封版硬契约（继承 v0.2.2.3）

### 1. Pipeline owner 必须逐表完成迁移

Task 05 不得只给旧 Pipeline 表增加 `smart_capture_id` 字段。必须逐表确认：

- 新记录的 `smart_capture_id` 是否为业务 owner；
- `workflow_run_id` 是否仅为 linked parent/history link，并在 independent 场景可为空；
- 现有 `NOT NULL`、FK、复合主键、唯一索引、部分唯一索引是否需要 SQLite table rebuild；
- discovery、feedback、Analysis item 等仍依赖 `workflow_task_id` 的记录，是否已经拥有不依赖 Workflow 的 Smart Capture domain task identity；
- legacy rows 无法回填时是否走只读兼容，而不是伪造 Smart Capture。

完整表级要求见 `E_状态_子任务_事件与实时传输契约.md` 和 Task 05/06。

### 2. 状态必须使用统一的语义契约

父子状态不得由不同模块自由解释。API 必须返回：

```text
waiting_reason
control_cause
state_version
capabilities: { start, pause, resume, retry, stop }
```

允许保留现有 Workflow legacy `status` 供历史兼容，但父 Workflow 的前端控制和父子转换必须使用 `control_state` 等语义字段。Smart Capture 自身不新增第二套 `control_state`；其控制 UI 统一由 `status + stage + waiting_reason + control_cause + capabilities` 推导。Smart Capture 的 `waiting_for_user`、`interrupted` 等状态必须同步更新数据库 CHECK、schema type、service、API 和测试。

`waiting_for_user` 是 Smart Capture **canonical lifecycle status**：新写入与 API 快照在需要用户/人工决策阻塞时必须返回该值；`waiting_next_batch` 只表示系统等待下一批/Prefetch 等非人工等待。历史数据若曾用 `waiting_next_batch + waiting_reason` 表示人工等待，只允许在 migration/read adapter 中映射，不能继续作为新写入形式。

### 3. 通用 child relation 与 completion event 必须持久化且幂等

父层必须有通用 child relation 表或等价持久化结构，至少保存 child type/ref、sequence、status、waiting reason、capabilities、result summary、timestamps、relation `state_version` 与最后接受的 `child_state_version`。

只有 **linked** child 产生 parent orchestration event；independent 不创建 hidden relation/event。Linked child event 必须带 `event_id/transition_id/child_relation_id/child_type/child_ref/state_version`。其中 event `state_version` 是**发送方 child lifecycle 版本**；relation 另存 `child_state_version`，只接受更高 child version。成功消费后 relation 自己的 `state_version` 再独立递增。Parent 同时依靠 `(child_relation_id,event_id)` 和 `child_state_version` 防重复/乱序，重复 completed、迟到 stop/failure、app restart 后重复消费都不能二次推进或覆盖更高优先级父状态。

**父子双层 authority 固定为：**

- `fj_smart_captures`（或 Smart Capture 专属表）是 child lifecycle/config/execution 的业务权威；
- `fj_workflow_children` 是 parent orchestration relation/projection 的权威，保存父层需要的 child 状态摘要、capability、result summary 和顺序；
- parent 不直接写 Smart Capture lifecycle；child 状态改变后通过持久化 event/事务投影更新 `fj_workflow_children`；
- `fj_workflow_children` 不能反过来成为第二个 Smart Capture lifecycle source；
- `fj_smart_captures.workflow_run_id` 仅作为 linked 导航/历史反规范化 link，通用 parent→child 关系以 `fj_workflow_children` 为 canonical relation；linked 创建时二者必须同事务一致。

### 4. Smart Capture 必须拥有独立 snapshot/polling

`GET /api/fine-job/smart-captures/current` 和 `GET /api/fine-job/smart-captures/{id}` 是对外完整 HTTP 路径；前端 client 若已有 `/api` 全局 prefix，则调用 `/fine-job/...`。二者指向同一 FineJob router，禁止再使用 `/smart-captures/...` shorthand。independent 不得依赖 Workflow SSE；linked parent 镜像、Smart Capture 详情和历史 Run 查看必须是三个独立状态源。

可以采用 polling 或以 `smart_capture_id` 为 scope 的事件流，但版本字段只能使用整数 `state_version`；任何改变 snapshot 可观察字段的提交都必须使其单调递增；必须支持按 `smart_capture_id + state_version` 断线恢复、terminal snapshot，以及 history 不污染 current/control。不得再新增或返回第二套 `revision` 字段。

### 5. Cutover 必须清理具体旧 live 入口

Task 09 后，以下代码不能继续作为 Smart Capture 的生产执行器：

```text
workflow_runs._on_capture_task_updated
workflow_runs._advance_after_capture_finished
advance_deep_job_search 作为 live Engine
smart_captures.resume_smart_capture 中的 resume + advance
fineJobWorkflowCodexController / App-level Workflow advance controller
```

旧函数可以作为历史兼容读取，但不能回退启动新的 BOSS/JD/Analysis/Prefetch。

### 6. 完整配置 owner 与 OFF 后处理

完整 `SmartCaptureExecutionConfig` 必须由 Smart Capture 持有，linked/independent 共用，不得把 ON 模式所需字段隐藏在 Workflow contract 中。

OFF completed 后的 Manual Analysis 必须以 `smart_capture_id` 为主 identity，保持 capture/parent 终态，不重复 child-completed，不重新占用 current，不重新启动自动 Engine。

详见 `E_状态_子任务_事件与实时传输契约.md`。

### 7. ExecutionConfig 从 Task 02 起就是 Smart Capture 身份的一部分

Task 02 在 linked/independent Smart Capture 创建时就必须把完整执行配置落到 Smart Capture 专属 owner（允许第一阶段采用 `execution_config_json`），与 parent/child relation/current pointer 同一事务提交。Task 05 之后迁的是 Pipeline 数据表 owner，不得让 Workflow contract 继续成为隐藏配置 owner。

### 8. Cutover 后 child start 只能通过通用 Child Adapter

Task 09 正式 Cutover 后：

```text
Parent Orchestrator
  → Child Adapter.start(child_type, child_ref)
      → SmartCaptureService.start(smart_capture_id)
          → pending → running
          → Smart Capture Engine
```

父层只允许发 `start/pause/resume/stop` 这类 child-level command，不得知道 BOSS/JD/Analysis/Prefetch 的内部启动细节。independent Smart Capture 也必须有明确 create-and-start 或 create→start API；不能依赖旧 Workflow `advance` 隐式启动。

## 三、当前源码再次核对的关键事实

1. Smart Capture router/service 已存在半成品，但 router 当前未注册到 `main.py`；startup recovery 也未接。
2. `ACTIVE_STATUSES` 当前未包含 `pending/waiting_for_user`，linked create 的 current 接管仍存在延迟语义。
3. `recover_interrupted_smart_captures()` 当前还会按最近活动/最近更新时间收敛 current，和“持久化 current identity”目标有冲突。
4. Smart Capture router 目前直接检查进程内 custom task；旧 `assert_collection_start_allowed()` 又在 Workflow 层维护另一套互斥，存在多入口互斥分散风险。
5. Workflow Run 当前仍直接启动 BOSS capture，`resume_smart_capture()` 仍可能调用 `advance_deep_job_search()`；`stop_smart_capture()` linked 时仍可能直接 cancel parent。
6. BossCapture 仍 `restoreLatest(false)`；`currentSmartCapture` 仍从 Workflow Run 临时拼装。
7. 历史 ID 非 mirror 时仍会被强制改回，历史查看语义被破坏。
8. Pipeline 表/服务大量仍以 `workflow_run_id` 为 owner。
9. 前端 `workflowCodexHandoff.ts`、`fineJobWorkflowCodexController.ts` 仍以 `FineJobWorkflowRun` / `workflow_run_id` 为核心；自动 controller 仍调用 Workflow `advance` 推 Prefetch。
10. MCP `finejob.ack_workflow_analysis_batch_started`、`list_workflow_analysis_items`、`get_workflow_analysis_item_context`、`save_workflow_analysis_item` 以及 `.agents/skills/finejob/SKILL.md` 的 deep_job_search 流程仍要求 `workflow_run_id`。
11. `CodexWorkspace.vue` / `CodexTerminalPanel.vue` 当前路由与任务定位仍依赖 `workflow_run_id`。
12. 现有 Workflow API tests 对 handoff/reservation/prefetch 有较多断言，应作为迁移 characterization 基线，不得简单删除。
