# 任务01：采集状态更新与轮询风险核对

## 1. 本次互斥修复后的结论

智能采集创建时已经在同一数据库事务内建立关联 Smart Capture 并占用 current 槽位。Smart 与 custom 的互斥判断使用该持久化身份和 custom capacity 记录，互斥正确性不依赖前端轮询。

Workflow Run 的主状态更新使用 SSE：页面通过 `/api/fine-job/workflow-runs/{workflow_run_id}/events` 建立 `EventSource` 长连接，服务端在状态变化时推送快照，并用 15 秒心跳维持连接。这是事件推送，不属于定时轮询。

## 2. 已识别的重复状态读取

当前 `BossCapture.vue` 会将智能采集的批次任务写入 `fineJobBossCapture` store。该 store 对 queued/running 任务会先在 0.5 秒后读取一次任务详情，随后每 1 秒读取一次 `/api/fine-job/boss-capture/tasks/{task_id}`。

页面同时订阅同一智能任务的 Workflow SSE；当上述批次读取更新 `updated_at` 时，页面又会调用 Workflow 详情接口刷新 Run。因此智能采集运行期间可能同时出现：

1. Workflow SSE 推送状态；
2. 每秒读取批次状态；
3. 每次批次状态更新后再读取一次 Workflow 状态。

这会产生重复快照来源，状态到达顺序不同会造成页面展示在相邻状态间切换。该问题不会影响后端互斥判定，但会影响页面稳定性和请求量。

## 3. 已在 Task01 范围内消除的轮询路径

旧的智能采集批次轮询链已经移除；当前页面按职责使用两条 SSE 状态流：

1. Smart Capture 主状态订阅 `/api/fine-job/smart-captures/current/events`，current 指针变化后再订阅 `/api/fine-job/smart-captures/{smart_capture_id}/events`；
2. linked parent 继续订阅 Workflow SSE；independent current 不建立父任务订阅；
3. `syncSmartCaptureTask` 保存到智能采集专用页面状态，不写入 custom capture store；
4. 智能采集不调用 `captureStore.resumePolling()`，也不再由批次 `updated_at` 变化间接刷新 Workflow。

两条 SSE 都发送首帧完整快照，使用 `state_version` 单调保护，服务端每 15 秒发送心跳；该调整保留当前 Workflow owner、Smart Capture current、custom capacity 和 API 契约，不改变 BossCapture 页面布局。

## 4. Task13 Smart Capture SSE 状态同步

Task13 的 current 接入已改为事件推送：

- 初始化：页面首次读取 `GET /api/fine-job/smart-captures/current`，再读取当前详情作为首屏快照。
- current 流：订阅 `GET /api/fine-job/smart-captures/current/events`，只接收 current pointer 变化。
- 详情流：按当前 `smart_capture_id` 订阅 `GET /api/fine-job/smart-captures/{id}/events`，接收该采集的状态、进度和领域快照。
- 服务端发布：Smart Capture 创建、绑定批次、控制动作、批次进度、Analysis 指导和 linked parent 控制提交后发布最新快照；队列只保留最新值。
- 页面保护：current、详情和历史 Context 分别使用身份与请求代际校验，同一采集只接受不低于已展示的 `state_version`。
- 退出与重连：页面卸载关闭两个 EventSource；浏览器 EventSource 自动重连，服务端重连后再次发送完整首帧。

本轮没有新增 Smart Capture 定时轮询；current、详情和 linked parent 的状态源彼此独立，不共享历史 Run 输入。

## 5. Task08B 新增的 Codex 自动交接轮询（本次复核确认，暂不修改）

- 位置：`apps/desktop/src/renderer/services/fineJobWorkflowCodexController.ts`、`apps/desktop/src/renderer/App.vue`。
- 引入任务：Task08B 将 App-level 自动交接从 Workflow identity 切换到 Smart Capture identity 时新增。
- 触发：桌面应用挂载后立即启动，不依赖岗位采集页面是否打开。
- 间隔：默认每 1.2 秒执行一次。
- 请求链：每轮先读取 `GET /api/fine-job/smart-captures/current`；存在非终态 current 时，再读取该任务的 Analysis Snapshot，并判断是否自动触发 Codex handoff。
- 结束：仅在 App 根组件卸载时停止。没有 current 或 current 已终态时仍保留定时器，并持续读取 current 接口。
- 现状风险：无任务时仍会产生约 50 次/分钟的 current 请求；任务运行时最多形成两次/轮请求；它与 Smart Capture current/detail SSE 并存，形成重复状态读取来源。
- 正确性边界：该轮询使用 `smart_capture_id`，没有回退 latest Workflow，也不调用 Workflow advance，因此不会恢复旧 Pipeline authority；主要风险是持续请求量、重复读取和后续状态源维护成本。
- 本次处理：按用户决定只记录，不修改现有轮询实现。

建议后续改成事件驱动：复用 current/detail SSE，在 Analysis Batch、Handoff、Prefetch promotion 等提交后递增 `state_version` 并发布快照；前端只在相关事件到达时读取一次 Analysis Snapshot，并按 `smart_capture_id + analysis_batch_id + state_version` 去重。

## 6. 该修复完成后仍保留的其他定时轮询

### 自定义 BOSS 采集任务

- 位置：`apps/desktop/src/renderer/stores/fineJobBossCapture.ts`。
- 触发：自定义采集任务处于 `queued` 或 `running`。
- 间隔：首次 0.5 秒，之后每 1 秒。
- 接口：`GET /api/fine-job/boss-capture/tasks/{task_id}`。
- 结束：任务变为 `completed`、`failed`，或读取失败。
- 用途：更新列表采集、继续采集和详情采集的进度。

该轮询是当前自定义采集唯一的实时状态来源。它的实现简单可靠，但在任务较多或采集时间长时会增加请求量；后续可单独为 Boss Capture task 建立 SSE 事件流，再移除该定时请求。

## 7. 不属于定时轮询的机制

- Workflow SSE 自动重连：连接断开后由浏览器 `EventSource` 重连，服务端先发送当前快照。
- SSE 15 秒心跳：维持连接和中间网络设备状态。
- 后端 `boss_capture_task_manager` 监听器：采集任务状态变化后同步 Smart Capture 快照，并在批次终态时推进 Workflow。
- 应用启动恢复：启动时一次性把失去执行器的任务收敛为可恢复状态。

## 8. 后续专项建议

后续若统一去除自定义采集轮询，应增加 Boss Capture task 的单任务 SSE 订阅，并约定：任务状态、进度、终态、断线重连首帧快照和订阅关闭条件。该专项应独立于 Task01，避免扩大 Smart Capture / custom capacity 的既定范围。
