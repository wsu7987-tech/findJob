# 一、必须继承的硬契约

以下契约不得修改。

## 1. Smart Capture 是 production live execution authority

Task09 后：

```text
parent orchestrator
  → ChildAdapter.start(child_type, child_ref)
  → SmartCaptureService.start(smart_capture_id)
  → Smart Capture Engine
  → Pipeline Repository
```

不得重新接入：

- Workflow Run live advance 驱动 Smart Capture；
- Workflow Run 直接启动 BOSS/JD/Analysis/Prefetch；
- App controller 调 `advanceFineJobWorkflowRun()` 推动业务 Pipeline；
- 通过 Workflow latest 推断 current Smart Capture。

旧 Workflow 路径只能继续承担：

- parent orchestration；
- history/read compatibility；
- linked parent control；
- legacy read adapter。

## 2. current identity 不得退回 Workflow 推断

Smart Capture current 必须继续以持久化 current pointer 为准。

以下均视为非终态、继续占据 current / collection business slot：

- `pending`
- `running`
- `pausing`
- `paused`
- `waiting_next_batch`
- `waiting_for_user`
- `interrupted`

以下为 Smart Capture 终态：

- `completed`
- `stopped`
- `failed`

## 3. parent / child 双 authority 不变

- `fj_smart_captures`：child lifecycle/config/execution 权威；
- `fj_workflow_children`：parent orchestration relation/projection 权威；
- child event 继续按 `child_state_version` 防旧事件/乱序事件；
- relation `state_version` 独立递增；
- independent Smart Capture 不得创建 hidden Workflow Run/relation/event。

## 4. Pipeline owner 不得回滚

新 Pipeline 数据业务 owner 继续使用 `smart_capture_id`。

`workflow_run_id` 仅允许作为：

- linked parent/history link；
- legacy read compatibility。

不得为了本次小修重新引入：

- independent 强依赖 Workflow；
- Pipeline 新写入按 Workflow fallback；
- 伪造隐藏 Workflow owner。

# 三、Task A：补齐 Task12 终态恢复硬契约

## A1. 已确认问题

v0.2.2.4 的 Task12 硬契约要求：

> 父真正终态后，新任务编排区重新出现，但上一轮 final result / child timeline 仍然保留，直到用户真正发起新任务。

当前 `TaskCockpitNew.vue` 进入页面时会：

1. 停止旧 Workflow SSE；
2. `workflowStore.setRun(null)`；
3. 调用 `workflowStore.restoreLatest(false, "task_cockpit")`。

而后端 `include_completed=false` 会排除：

- `completed`
- `completed_with_errors`
- `cancelled`
- `failed`

因此：

```text
父任务完成
→ 当前页面仍可看到 final result / timeline
→ 离开 TaskCockpit
→ 再进入 TaskCockpit
→ currentRun 被清空
→ terminal run 不再恢复
→ 上一轮 final result / timeline 丢失
```

这是 Task12 的明确验收漏项。

---

## A2. 目标语义

进入新驾驶舱 `TaskCockpitNew.vue` 时：

### 有非终态 task_cockpit Run

恢复该 Run，并保持现有行为：

- 隐藏可编辑编排区；
- 显示父状态；
- 显示 child timeline；
- 仅显示合法操作；
- 非终态 Workflow Run 使用 SSE；
- waiting / interrupted / child decision 等仍视为非终态。

### 没有非终态 Run，但存在 terminal task_cockpit Run

恢复最近一次 terminal Run：

- 编排区重新出现；
- 上一轮父状态仍显示；
- 上一轮 child timeline / result summary 仍显示；
- 不建立 Workflow SSE；
- 不显示 pause/resume/cancel 等运行态控制；
- 用户开始新任务后，旧 terminal Run 才被新 Run 替换为当前主展示对象。

### 没有任何 task_cockpit Run

只显示新任务编排区。

---

## A3. 推荐的最小实现

优先采用最小改动。

允许直接把：

```ts
workflowStore.restoreLatest(false, "task_cockpit")
```

改为能够恢复 terminal 的语义，例如：

```ts
workflowStore.restoreLatest(true, "task_cockpit")
```

但实现前必须检查：

- active Run 是否仍然正确优先；
- `restoreLatest(true)` 返回 nonterminal 时仍会启动 Workflow SSE；
- terminal Run 进入 `setRun()` 后不会建立 Workflow SSE；
- TaskCockpit 的 `workflowRunTerminal` / `canEditOrchestration` 仍正确；
- 新任务成功创建后 store 会自然切换到新 Run。

如果当前 latest API 的排序存在“terminal 覆盖仍活动 Run”的实际可能，则允许增加**最小的 active-first / terminal-fallback 恢复 helper**；但禁止新建第二套 Workflow current store 或改变后端 Workflow identity。

# 四、Task B：修复终态实时订阅状态的小缺口

这一部分只修已确认的终态错误语义，不做 SSE 总体架构重构。

---

## B1. Workflow store：terminal 时 `pollingActive` 必须为 false

当前 `fineJobWorkflowRun.ts` 的 `startPolling()` 名称保留兼容，但内部实际建立 Workflow SSE。

已确认的问题：

- `setRun(terminal)` 会调用 `stopPolling()`；
- 某些页面随后仍可能调用 `startPolling()`；
- `startPolling()` 先把 `pollingActive = true`；
- `ensurePolling()` 再因为 terminal 而不真正建立 EventSource。

结果可能出现：

```text
业务状态：terminal
pollingActive：true
实际 SSE：无
```

这是错误的内部状态语义。

### 必须改成

terminal Run：

```text
pollingActive = false
streamActive = false
eventSource = null
```

调用 `startPolling()` 时，如果：

- 没有 currentRun；
- currentRun 是 terminal；

必须保持 stop 状态，不得先置 `pollingActive=true`。

---

## B2. BossCapture：terminal linked parent 不应启动 Workflow SSE

`BossCapture.vue` 恢复 linked parent 时：

- 可以继续展示 terminal parent snapshot；
- terminal parent 只能作为只读父任务摘要；
- 不得启动 Workflow SSE。

即使页面误调用 `startPolling()`，Store 层也必须安全 no-op；页面层同时应避免发送无意义的启动调用。

---

## B3. BossCapture：terminal Smart Capture 不应建立 page-level detail SSE

当前全局 Codex controller 已经具备：

```text
terminal Smart Capture → close detail SSE
```

但岗位采集页面自身仍可能：

```text
存在 current → 建 detail SSE
```

包括 terminal current。

本次小修要求：

- 页面仍可通过 current snapshot 展示 terminal 结果；
- terminal Smart Capture 不建立 `/smart-captures/{id}/events` page-level detail SSE；
- active / waiting / interrupted Smart Capture 的 detail SSE 行为保持不变；
- 不在本任务内统一 App-level 与 page-level current SSE；
- 不在本任务内建设统一 Realtime Hub。

---

# 七、本轮必须保护的回归场景

除了新增测试，至少确认以下历史契约没有被小修破坏。

## Parent / child

- linked Smart Capture child 完成后 parent 正确完成或启动 next child；
- child stopped → `child_cancelled_waiting_decision`；
- child failed → `child_failed_waiting_decision`；
- failed child 不允许 retry；
- skip 只表示 parent orchestration 跳过，不改变 child hard terminal；
- interrupted 可恢复；
- parent pause 优先级不被迟到 child event 覆盖；
- terminal parent 不被迟到 event 二次推进。

## current / history

- current Smart Capture A 不被历史 B 污染；
- 查看历史 Workflow B 不改变 linked parent A；
- history 不改变 current/control/SSE target；
- independent 不依赖 Workflow current/latest。

## Codex

- App auto handoff 使用 `smart_capture_id`；
- 不回退 latest Workflow；
- 不调用 Workflow advance；
- Codex controller 不恢复 1.2 秒周期轮询；
- 同一 Analysis Batch 不重复 handoff；
- Codex busy → idle 后仍有合法重试能力。

## collection capacity

- pending / paused / waiting_for_user / interrupted Smart Capture 仍占 business slot；
- Smart 与 custom 互斥；
- terminal 后释放执行容量符合既有规则；
- 不因 terminal UI 修复改变 capacity 语义。
