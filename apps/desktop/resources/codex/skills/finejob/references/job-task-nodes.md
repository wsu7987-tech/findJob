# 岗位任务节点

本文件定义可组合的岗位业务节点。根据用户目标选择节点并动态串联；示例目标用于说明编排方式，不构成固定任务模式。

## 一、先确定完成口径

开始前把自然语言目标转换成完成契约。数量必须绑定明确的正式结果：

| 用户表达 | 默认计数口径 |
| --- | --- |
| 完成 N 条岗位筛选 | N 个唯一历史岗位已保存本次正式筛选结果；`pass`、`review`、`reject`、`exclude` 都属于已完成筛选 |
| 筛选出 N 条候选岗位 | N 个唯一岗位的结果为 `pass` 或 `review` |
| 筛选出 N 条明确合适岗位 | N 个唯一岗位的结果为 `pass` |
| 完成 N 条投递建议或岗位评估 | N 个唯一岗位的结构化评估已经成功保存 |
| 找出 N 条建议投递岗位 | N 个唯一岗位的评估结论为 `recommend`；已保存的 `review` 和 `reject` 不计入目标数量 |
| 实际投递或发起沟通 N 条 | 当前 FineJob 只支持受控的 BOSS 默认招呼动作；只有动作状态为 `succeeded` 才计数 |

用户已经说明不同口径时按用户定义。用户只说“完成 N 条岗位投递”时，先确认是生成投递建议、找出建议投递岗位，还是执行真实招呼；三者的完成结果和授权范围不同。

所有数量按唯一 `history_job_id` 计数。重复采集、重复筛选、重新获取 JD、重新保存同一岗位建议都不增加完成数量。

## 二、共享状态

在当前任务中维护以下状态，不新增 FineJob 业务表：

- 完成契约和目标数量。
- 岗位筛选策略 ID。
- 建议投递策略 ID 及其关联的筛选策略、具体简历。
- 当前统一评估上下文修订 ID。
- 已使用的搜索词与城市组合。
- 当前采集任务 ID。
- 已筛选、已取得 JD、已保存评估、已路由和已执行成功的唯一岗位集合。
- 当前搜索页的 `has_more`、最近新增数量和连续无新增次数。
- 用户要求和平台返回的停止原因。

状态只用于本次编排；岗位、筛选、JD、评估、审批和动作结果继续写入 FineJob 现有正式位置。

## 三、任务节点

### J0：确认运行能力

**目的**：确认当前目标所需的 FineJob 能力可以执行。

**前置**：无。

**动作**：调用一次 `finejob.get_capabilities`。

**完成标准**

已取得注册工具及当前运行状态，并按目标区分阻断项：

- 新岗位采集需要 `job_capture_ready`。
- 已有岗位读取、筛选结果查看和建议数据读取不要求 BOSS 执行器在线。
- 真实招呼执行需要相应执行器、权限和队列状态。

**后续注意**：不得用 BOSS 执行器离线或 `risk_paused` 阻断采集、筛选、JD 获取和建议生成。

### J1：解析正式策略

**目的**：确定本次节点应使用的正式策略及其关联关系。

**前置**：J0 已完成。

**动作**：调用 `finejob.list_job_strategies(enabled_only=true)`，按用户给出的名称或 ID 选择现有策略。

**完成标准**

- 筛选任务取得唯一的岗位筛选策略。
- 建议任务取得唯一的建议投递策略，并确认其关联的筛选策略和具体简历。
- 启用搜索词和城市顺序已经取得。

**后续注意**

不创建或修改策略。名称无法唯一匹配、用户同时指定的策略关联冲突时，向用户说明具体冲突并等待选择。建议投递策略已经关联具体简历时，不再独立要求 `candidate_profile_id` 非空。

### J2：准备统一评估上下文

**目的**：取得供多个岗位共同使用的候选人事实、QA、具体简历和建议策略上下文。

**前置**

- 目标包含岗位评估、投递建议或招呼语。
- J1 已取得建议投递策略。

**动作**：调用一次 `finejob.get_job_evaluation_context`，传入建议投递策略 ID 和实际筛选策略 ID。

**完成标准**：取得可用的上下文修订、具体简历 ID 和相关策略内容。

**后续注意**

- 当前没有上下文时沿用 FineJob 自动生成并保存的结果。
- 上下文过期且工具要求确认时，只让用户选择一次重新生成、继续使用当前版本或取消。
- 当前任务后续所有岗位复用同一上下文修订；版本冲突后才重新读取。
- 在可能创建评估路由前，把工具返回的自动招呼状态告诉用户。

### J3：选择岗位来源

**目的**：决定复用历史岗位还是采集新岗位。

**前置**：J1 已完成，完成契约已明确是否要求新采集。

**动作**

- 允许复用历史岗位时，调用 `finejob.search_jobs` 查找已经满足所需筛选状态、尚未完成后续节点的岗位。
- 目标要求新采集、历史岗位不足或历史状态不满足时，选择 J4。

**完成标准**：得到可供下一节点处理的唯一岗位集合，或者确定需要启动新采集。

**后续注意**：历史岗位必须使用当前保存状态。需要重新应用策略的岗位应进入当前采集任务后调用 J6，不根据终端记忆自行重算并冒充正式结果。

### J4：首次采集搜索组合

**目的**：使用正式筛选策略开始一个新的搜索词与城市组合。

**前置**

- J0 确认专用浏览器可用。
- J1 已取得筛选策略、启用搜索词和城市。
- 当前没有可继续使用的采集任务，或旧搜索组合已经耗尽。

**动作**

首次调用 `finejob.start_job_capture`：

- 传入筛选策略 ID。
- 每个新搜索组合首次使用 `pages=1`。
- 第一个组合默认使用策略第一条启用搜索词和第一个城市。
- 后续组合只能从同一策略的其他启用搜索词和城市中选择。

使用 `finejob.get_operation_status(resource_type="capture_task")` 等待完成。

**写入结果**：岗位由 FineJob 写入历史采集，任务返回当前岗位列表、实际搜索词、城市、`has_more` 和续采能力。

**完成标准**：采集任务结束并取得正式任务 ID；即使没有岗位也应取得明确完成或失败状态。

**后续注意**：同一搜索词与城市仍可续采时，不重复调用 J4。采集完成后选择 J6。

### J5：原页面继续下滑

**目的**：在同一搜索组合中扩大岗位集合。

**前置**

- 已有完成或停止的采集任务。
- `continuation_available=true` 且 `has_more=true`。
- 原搜索页仍由 FineJob 保留。

**动作**

调用 `finejob.continue_job_capture`，沿用同一 `capture_task_id`，页数使用用户参数或任务给出的单次页数。等待同一任务完成后选择 J6。

用户要求停止正在运行的列表采集时，调用 `finejob.stop_job_capture`，再查询到 `list_stopped`。

**写入结果**：新增岗位追加到同一任务和现有历史采集；已获得岗位继续保留。

**完成标准**：取得本次新增岗位数、累计岗位数、实际下滑页数和最新 `has_more`。

**后续注意**

- 继续采集不创建新任务，不重新打开第 N 页。
- 每次续采后必须重新执行 J6，再根据完成契约决定下一节点。
- `has_more=false` 时选择下一个搜索组合。
- 连续五次续采没有新增唯一岗位时，视为当前组合无有效增量，选择下一个组合。
- 停止采集保留浏览器和搜索页；关闭专用浏览器会失去续采条件。

### J6：保存岗位筛选结果

**目的**：使用正式筛选策略评估当前采集任务内的岗位，并把结论写入 FineJob。

**前置**：J4 或 J5 已完成，且已有采集任务 ID。

**动作**：调用 `finejob.apply_job_filter`。

**写入结果**：当前任务和历史岗位保存最新 `filter_status`、原因、缺失信息和策略 ID。返回结果同时提供采集任务内 `job_id` 与 `history_job_id`。

**完成标准**：本次岗位均取得正式筛选结果，完成契约中的相应唯一岗位集合已经更新。

**后续注意**

- 详情采集使用任务内 `job_id`。
- JD 读取、建议保存和后续业务使用 `history_job_id`。
- `exclude` 保留具体冷却、黑名单或公司排除原因。
- 当前自动推荐任务只把本轮筛选为 `pass` 或 `review` 的岗位作为 J7、J8 候选；用户后续手动获取详情或重新评估时仍使用现有入口。
- 对依赖候选岗位的目标，本页 `selected_jobs` 为空只表示本页没有候选岗位。只要目标数量尚未达到且 `continuation_available=true`、`has_more=true`，必须直接选择 J5，不能结束整个任务。
- 达到筛选完成标准即可结束；数量不足时根据 `has_more` 选择 J5，当前组合耗尽后选择 J4。

### J7：获取当前岗位 JD

**目的**：为需要评估的候选岗位取得并保存当前 JD。

**前置**

- J6 已完成。
- 岗位满足完成契约规定的候选条件，通常为 `pass` 或 `review`。
- 当前采集任务内存在对应 `job_id`。

**动作**

将尚未完成详情的任务内岗位 ID 传给 `finejob.collect_job_details(force=false)`，等待任务结束。然后按 `history_job_id` 调用 `finejob.get_job_jd` 读取当前正式 JD 和详情版本。

**写入结果**：FineJob 覆盖保存岗位当前 JD、详情状态和详情版本。

**完成标准**：每个待评估岗位都有 `detail_status=completed` 的当前 JD，或已有明确失败原因。

**后续注意**：失败岗位不进入依赖完整 JD 的评估计数。目标数量不足时返回 J5 或 J4 补充候选岗位。用户明确要求重新获取已有详情时才使用 `force=true`。

### J8：生成并保存岗位评估

**目的**：基于统一上下文和当前 JD 生成结构化评估或投递建议。

**前置**

- J2 已取得统一上下文修订。
- J7 已取得当前 JD 和详情版本。
- 岗位尚未计入本次已完成评估集合。

**动作**

1. 使用同一上下文修订、实际两项策略和该岗位当前 JD 生成符合 `finejob.save_job_evaluation` 当前工具契约的结构化结果。
2. 事实只来自统一上下文或当前 JD；证据不足时使用 `review` 并填写缺失信息。
3. 每生成一个结果立即调用 `finejob.save_job_evaluation`，传入 `history_job_id`、当前详情版本、上下文修订 ID、两项策略 ID 和完整评估字段。

**写入结果**：历史岗位最新建议、岗位评估记录以及现有待确认或自动路由结果。

**完成标准**：保存工具返回评估资源 ID 及路由状态，岗位加入本次已保存评估集合。

**后续注意**

- 保存失败的岗位不计数，保留原因并处理下一岗位。
- “完成 N 条评估”按保存成功数计；“找出 N 条建议投递岗位”只按 `recommend` 数计。
- 自动招呼开启时，`recommend` 可能沿用现有规则直接创建动作；如实报告，不把动作创建表述为发送成功。
- 数量不足时，从尚未评估的候选岗位继续；候选耗尽后返回 J5 或 J4。

### J9：创建或执行真实沟通动作

**目的**：在用户明确要求真实对外沟通时，创建预览并请求受控执行。

**前置**

- 用户目标明确包含真实发送。
- 已有当前岗位评估及所需文本。
- J0 已确认相关执行能力，或系统能够创建待确认项。

**动作**：按工具能力创建打招呼预览，并使用最新资源版本请求执行。返回确认要求时等待用户在 FineJob 处理；动作创建后查询权威状态。

**完成标准**

- 任务目标只是进入待确认：正式待确认资源已经创建。
- 任务目标是真实发送：动作状态为 `succeeded`。

**后续注意**：`pending`、`approved`、`queued`、`leased` 都不等于真实发送成功。不得为了凑满 N 条绕过确认、版本或平台校验。

### J10：核对数量并结束

**目的**：判断整个用户目标是否真正完成，并给出可核对的结果。

**前置**：至少执行了一个产生正式业务结果的节点。

**动作**：按完成契约重新计算唯一岗位数量，并核对 FineJob 返回的正式状态。

**完成标准**

满足以下任一条件：

- 达到目标数量和规定状态。
- 用户要求停止。
- 所有启用搜索组合耗尽。
- 平台登录、验证或限频形成明确阻断。
- 继续执行需要新的用户选择或授权。

**最终汇报**

- 实际使用的策略、搜索词和城市。
- 采集与唯一岗位数量。
- 筛选各状态数量。
- JD 成功与失败数量。
- 已保存评估、`recommend/review/reject` 和路由数量。
- 待确认、动作队列和实际成功分别统计。
- 未完成差额、失败岗位及停止原因。
- 可以继续时说明应从哪个节点继续。

当前页岗位全部为 `exclude/reject`、当前页候选岗位为零、一次采集或筛选调用已经完成，都不属于整个目标任务的停止条件。

## 四、两个初始目标的动态编排示例

### 完成 N 条岗位筛选

`J0 → J1 → J4 → J6 → J10`

数量不足时：

- 当前组合仍有更多结果：`J5 → J6 → J10`。
- 当前组合耗尽：换策略内搜索词或城市后执行 `J4 → J6 → J10`。
- 达到用户定义的筛选计数后结束，不执行 JD、评估或沟通节点。

### 完成 N 条投递建议

`J0 → J1 → J2 → J3`

历史候选不足时组合 `J4/J5 → J6`，随后执行：

`J7 → J8 → J10`

保存成功数量不足时，优先处理尚未评估的候选岗位；候选耗尽后返回 J5 或 J4。只有用户目标明确包含真实沟通时才继续 J9。

首屏岗位全部被排除时，若原页面仍可续采，则立即执行 `J5 → J6`；只有当前组合 `has_more=false` 时才改用下一个启用搜索词或城市。所有组合耗尽前不能以“没有候选岗位”结束任务。
